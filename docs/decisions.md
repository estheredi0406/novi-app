# Decision log

Each entry records a choice, why it was made, and what was considered instead. Entries are never rewritten or deleted; a changed decision gets a new entry that names the one it supersedes.

## Sprint 0: Foundations

### D1. One repository for the whole system (13 Oct 2026)
The API, mobile app, mock MFI and shared code live in one npm workspaces repository. The app and API import the same type definitions from packages/shared, so if the shape of a contribution changes on one side, the other fails to compile before the demo, not during it. A feature touching both sides is one commit. Considered: separate repositories; rejected because shared types would have to be published and versioned separately.

### D2. Novi never holds money (13 Oct 2026)
Contributions go to an account at a licensed microfinance institution. Novi keeps the rules and the ledger and instructs the MFI to pay out. Under BCEAO Instruction n°001-01-2024, only banks, microfinance institutions, payment institutions and e-money issuers may provide payment services; Novi holds none of these licences.

### D3. Every outside service sits behind an interface (13 Oct 2026)
Identity checks, payments, the MFI and SMS are reached through IdentityProvider, PaymentProvider, MfiAdapter and SmsProvider. The demo uses mock versions; a real provider replaces one file. Reasons: FedaPay documents sandbox test numbers for Benin only, ANID identity checks are open to partners only, and Africa's Talking does not offer SMS or USSD in Togo in production.

### D4. Money is stored as whole numbers of FCFA (13 Oct 2026)
FCFA is used without a smaller unit in daily trade, and decimal numbers in JavaScript cause rounding errors (0.1 + 0.2 gives 0.30000000000000004). Every amount is an integer number of FCFA.

### D5. The ledger is append-only (13 Oct 2026)
A ledger entry is never edited or deleted; a correction is a new entry that references the one it corrects. Every member can then trust that the history she sees is the history that happened, which answers the trust problem behind organiser fraud in tontines.

### D6. Node.js 24 (13 Oct 2026)
Supersedes the Node 20 choice in the original build brief. Node 20 reached end of life on 30 April 2026 and no longer receives security fixes (nodejs.org/en/about/previous-releases); Node 24 is the current long-term support line. Pinned in .nvmrc and in the engines field of package.json so development and hosting run the same version.

### D7. Local database for development; Railway for deployment only (13 Oct 2026)
PostgreSQL runs on the developer's laptop during Sprints 0 to 8; Railway hosts the API and database from Sprint 9, with one trial deployment of the API at the end of Sprint 0 to prove the pipeline. Railway's Free plan gives $1 of credit per month and its Hobby plan costs $5 per month (docs.railway.com/pricing), which would not keep an API and a database running continuously while no users exist; trial databases are deleted 30 days after credits expire. A local database also works offline. Moving changes only DATABASE_URL.

### D8. PostgreSQL 18 with a dedicated, limited user (13 Oct 2026)
Development uses PostgreSQL 18 on port 5432. The API connects as novi_app, which owns only the novi_dev database, never as the postgres administrator (least privilege). novi_app has CREATEDB because Prisma creates a temporary shadow database to check each migration.

### D9. Prisma ORM 7.10.0, pinned exactly (13 Oct 2026)
On 13 Oct 2026 the npm registry tagged prisma 8.0.0-rc.22 (a release candidate) as latest, with stable 7.10.0 under the prev tag. Novi uses the stable line. prisma, @prisma/client and @prisma/adapter-pg are installed with exact versions because they must always match. The generated client is written to apps/api/src/generated so it stays inside the TypeScript rootDir, and is ignored by Git because prisma generate rebuilds it.

### D10. Expo SDK 57, blank template, Expo Go until native modules are needed (14 Oct 2026)
The mobile app starts from Expo's blank TypeScript template so every file is written and explained by the author. It runs in Expo Go during development; a development build replaces it when a feature needs native code Expo Go lacks (WatermelonDB, Sprint 6). No web target: Novi's users are on phones, and the MFI console is a separate web project.

### D11. Known npm audit warnings deferred to the security pass (14 Oct 2026)
create-expo-app reported 22 vulnerabilities, mostly in development tooling. npm audit fix --force is not used because it upgrades packages beyond the versions Expo SDK 57 supports. They are reviewed in Sprint 9 with npm audit --omit=dev, which lists only issues in shipped code.

## Sprint 1: Sign-up and login

### D12. Identity is verified before an account exists (14 Oct 2026)
Under BCEAO Instruction 003-03-2025, Art. 14(5), a remote client's first transaction may only happen after her identity is verified. At sign-up, after consenting, the member enters her NIU, full name and date of birth; the mock ANID service checks they match its record and sends a one-time code to the phone on ANID's record, as MOSIP-based systems do. Names are compared ignoring capitals and extra spaces; everything else must match exactly. After 3 failed attempts the NIU is blocked for 24 hours and she is told to visit the MFI with her ID card. No account is created until verification succeeds, so there is no unverified account state and no ID queue for MFI officers. Supersedes the build brief's "accept invitations but cannot pay" state. Known limitation: the phone on ANID's record may not be hers today; the branch fallback covers this.

### D13. Women traders first, open to every informal trader (14 Oct 2026)
Novi is designed around informal women traders, the group most affected by the problem: women hold 69.7% of jobs in Togo's informal units (INSEED & AFRISTAT, ERI-ESI 2017) and 45.4% of women own a financial account against 70.0% of men (Global Findex 2024). It starts in Lomé's markets but serves any informal trader: informal work extends well beyond markets (91.6% of jobs in Togo are informal, same survey), and nothing excludes men. A member records the neighbourhood where she trades (required, never an exact location) and a market only if she trades in one. Novi stores no gender: the product does not need it, and the women focus is measured in the research, not in the database. Interface text uses neutral wording, including in gendered languages such as French.

### D14. Secrets live only in environment files (14 Oct 2026)
The database address, JWT_SECRET and NIU_HASH_KEY are read from apps/api/.env (and .env.test for tests), which Git ignores; the API refuses to start if one is missing. .env.example holds placeholders only, so another developer knows what to set without seeing real values. On 16 Oct 2026 the real local password was found in .env.example; it was replaced with a placeholder and both database passwords were changed, because Git history keeps the old value. Every commit is now checked with git diff --staged first.

### D15. Two names: legal name and display name (14 Oct 2026)
legalName comes from the ANID check, appears on the ACEV and cannot be changed in the app. displayName is chosen by the member and is what her group sees. Groups never see the legal name or phone number.

### D16. Easy PINs are refused (14 Oct 2026)
A PIN made of one repeated digit, a straight sequence in either direction, or one of the most common choices is refused, on the phone at once and by the API with PIN_TOO_WEAK. The rule lives in packages/shared so app and API apply exactly the same one.

### D17. No fingerprint or face unlock (14 Oct 2026)
Phones in Lomé are often shared within a family. Device biometrics trust every fingerprint or face enrolled on the phone, which may include someone else's, so Novi relies on the PIN only she knows.

### D18. PIN lockout grows with each lock (14 Oct 2026)
Five wrong PINs lock the account for 15 minutes, then 1 hour, then 24 hours. A right PIN resets the count and the escalation. The lock is checked on the server, so reinstalling the app does not lift it.

### D19. Short access tokens, rotated refresh tokens, a session check on every request (15 Oct 2026)
Access tokens last 15 minutes. Refresh tokens last 30 days, are stored only as SHA-256 hashes and work once: each use returns a new pair. A retired refresh token presented again after a 30-second grace (for weak connections that send twice) revokes every session of that member. Every request also checks that its session is still open, so logout and PIN reset take effect at once.

### D20. Forgotten PIN is reset by SMS and logs out every phone (15 Oct 2026)
A PIN reset needs the SMS code for her number, then a new PIN typed twice. It revokes all sessions, clears any lockout, and records pinChangedAt so a reset stamp issued earlier cannot be used again.

### D21. Expo Router and Noto fonts (15 Oct 2026)
Screens use Expo Router (file-based routes, typed routes). Noto Sans and Noto Sans Display are loaded before anything is shown, because they contain the Ewe letters (ɖ ƒ ɣ ŋ ɔ ɛ ʋ) that system fonts may lack.

### D22. Interface text as translation keys (15 Oct 2026)
All text lives in en.json, fr.json and ee.json, read with i18next. The API sends message keys, never sentences. French must contain every English key (checked at compile time); Ewe falls back to French until a native speaker has reviewed it. A compile-time check fails if the API can send an error key that has no English text.

### D23. PIN at every opening; one session per phone (15 Oct 2026)
Tokens are cleared each time the app starts, so Novi asks for the PIN at every opening; only her phone number and display name stay on the phone, in secure storage. Logging in on a phone closes that phone's previous session (reason REPLACED).

### D24. Sign-up protections (16 Oct 2026)
Sign-up answers the same whether or not a number already has an account: the SMS to a registered number says so instead of carrying a code, and nothing on screen reveals it. Codes are limited per phone (60 seconds apart, 5 per hour, counted in the database) and per address (in memory). Identity checks are limited to 3 failures per NIU in 24 hours. The sign-up draft (stamps and PIN) is kept in memory only and is lost if the app closes.

### D25. Multi-step login and PIN reset live in one screen each (16 Oct 2026)
Login (PIN, lockout countdown, new-phone code) and PIN reset (phone, code, new PIN) are each one screen with steps, not one screen per step. The PIN typed before a new-phone check, and the stamp from the reset SMS, stay in that screen's memory only: never in storage, never in the route address, and gone when the screen closes. Sign-up keeps separate screens because its steps are long and each one is checked by the API before the next.

## Sprint 2: Groups and rules

### D26. A group counts towards the 3-group limit from the moment she accepts its rules (16 Oct 2026)
A group counts towards a member's "at most 3 active groups" while it is PROPOSED (and she has accepted), STARTING or ACTIVE, not only once it is ACTIVE. Otherwise a member could accept many groups at once, and when they all start she could not pay into all of them, so each group would fail for everyone else in it.

### D27. "One completed cycle" means a group she belonged to reached COMPLETED (16 Oct 2026)
A member may start 2 groups. To start a third, she must have been a member of a group that reached COMPLETED: she kept paying until every member had received the pot. Receiving her own pot once is not enough, because she could stop paying straight after her turn.

### D28. A group has between 3 and 15 members (16 Oct 2026)
With 2 members a group is a private arrangement, and one missed payment empties half the pot. 15 is the upper limit already set by the product rules.

### D29. Rules are versioned; a group starts only when every seat accepted the current version (16 Oct 2026)
Each change to a group's rules (amount, frequency, size, payout order) creates a new version, and every acceptance falls back to "not yet". The organiser can start the group only when every remaining seat has accepted the current version. Silent seats must be removed first, which changes the size and therefore creates a new version that everyone accepts again. This proves later that every member agreed to the exact rules her money followed.

### D30. Groups pay weekly or monthly, on a fixed day (16 Oct 2026)
A group's rules set WEEKLY (day 1 Monday to 7 Sunday) or MONTHLY (day 1 to 28). Weekly matches market-day tontines; monthly suits members paid by the month. Monthly days stop at 28 so every month has the due day.

### D31. Contributions are between 100 and 1 000 000 FCFA (16 Oct 2026)
A group's contribution must be a whole number of FCFA from 100 to 1 000 000. The bounds are a safety net against typing mistakes (50 000 000 instead of 5 000), not a product rule; they are deliberately wide and will be confirmed with the partner MFI.

### D32. Zod checks the shape of a request; the rules engine checks the rules (16 Oct 2026)
Routes use Zod only to check that the right kinds of values were sent (a number, one of WEEKLY or MONTHLY) and to refuse unknown fields. Whether a value is allowed (3 to 15 members, 100 to 1 000 000 FCFA) is decided only by groupRules.ts, so each rule lives in one place and always answers with the same error code. A person with no seat in a group is told the group does not exist (404), not that access is forbidden, so group IDs cannot be probed.

### D38. Invitations go to a phone number; a seat exists only once she answers (20 Oct 2026)
The organiser invites by phone number. The invitation holds a place in the group (it counts towards the size) but is not a seat: the person gets a seat only when she answers. Inviting works, and looks, the same whether or not the number has a Novi account: the SMS text is the same, and the group sees only a masked number ("+228 90 •• •• 56") until she answers, so the organiser cannot use invitations to find out who uses Novi (the same rule as login, D24). A number invited before it had an account sees the invitation as soon as it signs up, because invitations are found by her verified phone number. The organiser can withdraw an invitation or remove a seat before the group starts; her own seat cannot be removed (she cancels the group instead).

### D39. Answering a group: accept, ask for a change, or say no (20 Oct 2026)
She accepts or asks for a change only once the organiser has proposed the group, and her answer carries the version of the rules she read: if the organiser changed them meanwhile, the answer is refused (RULES_CHANGED) and she reads the new version (D29). Accepting checks her 3-group limit (D26). Asking for a change keeps her place and shows her note to the group; the organiser answers by changing the rules (everyone answers again) or by removing her seat. She can say no at any point before the group starts, including while it is a draft and after she accepted; her place is freed and the group never sees her name, so saying no costs her nothing with the organiser. Her seat is created from the invitation the first time she answers (D38). The organiser does not answer her own group: proposing it is her acceptance, cancelling it is her way out.

### D40. No group search or discovery: a group is reached only by invitation (20 Oct 2026)
There is no list of open groups, no search bar for groups or members, and no "groups near you", even at market level. A person learns that a group exists only when its organiser invites her phone number (D38), and a group's page answers 404 to anyone without a seat or a pending invitation (D32). Reason: a list of groups shows who saves, how much, how often and in which market, which tells a thief or a jealous relative where cash gathers on which day, and tells others who is in which group; tontines in Lomé are formed between people who already trust each other, so discovery adds risk without matching how groups form. Supersedes "market-level discovery" and "invite by search" in the brief (F6 is now: invite by phone number; answer). The profile's area and market are kept for the research and for matching a group to an MFI branch; nothing shows them to other members.

### D41. Payout order: drawn once by Novi, or fixed by the organiser and accepted by everyone (20 Oct 2026)
A group's rules say DRAWN (the default) or FIXED. DRAWN: Novi draws the order when the group starts, with Fisher-Yates and the operating system's secure random numbers (Node.js crypto.randomInt), so every order is equally likely and nobody, Novi included, can steer it; the draw happens once and is recorded in the audit trail, and a retry never draws again, so nobody can retry until the draw suits them. FIXED: once every seat is taken, the organiser sets who is paid first, second and so on (for example Abla first because her shop rent is due); the order is saved as a new version of the rules, so every member accepts the exact order before the group can start (D29). The order must name every member once, and is checked again at the start in case someone left. Considered: paying in the order members accepted (rejected: it rewards speed, not need, and late answerers always go last).

### D42. Starting a group: Novi checks and fixes the order, then the MFI opens the account (20 Oct 2026)
The organiser starts the group. Novi checks every rule (every seat accepted the current version, D29; her start limit, D27), fixes the payout order and moves the group to STARTING, from which nobody can leave or change anything. Novi then asks the MFI to open the group's account and, once it answers, the group is ACTIVE. The MFI is told the group's totals only (contribution, number of members, frequency), never names or phone numbers (D33). If the MFI does not answer, the group waits in STARTING with its order kept, and the organiser can try again; Novi sends its own group ID with each request so a retry never opens a second account. The database is never kept waiting on the MFI: the two steps are separate transactions. The MFI sits behind an MfiAdapter interface with a mock until a partner offers an API (D3).

### D43. Guarding against a wrong number: four checks before the wrong person can join (20 Oct 2026)
A typo in an invited number could let a stranger accept, receive a pot and stop paying, the classic tontine loss. Four checks: (1) before the SMS is sent, the organiser sees the whole number she typed and confirms it; (2) the invitation screen tells the invited person to accept only if she knows the organiser, and to say no if the invitation reached her by mistake; (3) before the start, the organiser is shown every member's name and asked whether she knows each of them in person; (4) the organiser, and only she, sees part of each member's number next to her name ("Abla, +228 90 •• •• 02"), so she can check that the person who accepted is the number she meant. Showing the organiser 4 digits of a number she typed herself reveals nothing new; other members still see names only (D15). Until the start, the organiser can remove anyone (D38). Considered: showing the organiser the invited person's legal name (rejected: it would reveal an ANID name before the person agreed to join, against D15 and D38).

## Sprint 3: Money in

### D44. The calendar: round 1 is due on the first due day after the start (21 Oct 2026)
When the group becomes ACTIVE, Novi writes one round per member. Round N is paid out to the member whose payout position is N (D41), and is due on the Nth due day after the start: never the start day itself, so nobody is asked to pay within hours of the start, and the MFI has time to open the account. Weekly rounds are 7 days apart, monthly ones on the same day each month (days stop at 28, D30). Dates are calendar days in UTC, because Togo uses GMT all year with no summer time. A round can be paid from the day after the previous round's due date; earlier rounds can still be paid late, later ones not yet.

### D45. A payment is credited once, only after the provider confirms it (21 Oct 2026)
She taps Pay; Novi asks the payment provider to send a request to her own verified number (never another wallet), and she confirms on her phone with her mobile money PIN, which Novi never sees. The payment counts only when the provider says the money moved. Each webhook is checked: its signature (HMAC-SHA256, header X-FEDAPAY-SIGNATURE, older than 5 minutes refused, as in FedaPay's own library); the same delivery twice is recognised by a hash of its body; and its content is not trusted, so Novi asks the provider for the transaction's status, as FedaPay advises. A payment whose amount differs from the contribution is not credited and is flagged for the MFI officer. Crediting is idempotent: the update to PAID only matches a payment not yet PAID, and the ledger accepts one line per payment. If a webhook is lost, her "check" asks the provider directly. One request per round at a time; a new one after 5 minutes or a failure.

### D46. The ledger is append-only in the database itself (21 Oct 2026)
D5 is enforced by PostgreSQL, not only by the code: a trigger on ledger_entries refuses every UPDATE and DELETE, so neither a bug nor anyone using the app's database account can change history. A mistake is fixed by adding a CORRECTION line that points to the line it corrects. Payment requests (contributions) are a separate table that does change (PENDING, then PAID or FAILED), because a request is not money; only a confirmed payment becomes a ledger line.

### D47. FedaPay is called directly, not through its Node library (21 Oct 2026)
FedaPay's official Node library (fedapay 1.2.5) depends on axios 0.28, for which npm audit reports several high-severity advisories. Novi calls FedaPay's REST API with Node's built-in fetch instead (create the transaction, get a token, "send now" with mode moov_tg or togocel, read the status back), using the request and response shapes from the library's own tests. The adapter sits behind PaymentProvider (D3) and is selected with PAYMENT_PROVIDER=fedapay; it has not yet been run against the sandbox, which needs a FedaPay account and keys. Tests and the laptop use a mock that signs its webhooks the same way.

## Sprint 4: Money out

### D48. A pot is sent on its due date, and only when it is full (22 Oct 2026)
On a round's due date Novi instructs the MFI to send the pot to the member whose turn it is. Before the due date nothing is sent, even if everyone has paid early: members expect the pot on the agreed day. If the day has passed and someone has not paid, the payout is HELD, never sent short, and every member sees "Pot held: waiting for 1 payment". The moment the last payment is confirmed, the held pot is released without waiting for the next run of the payout job. Considered: paying out a partial pot on time (rejected: the member whose turn it is would be short-changed by someone else's lateness, and the group would owe her the rest); a further hold rule from the brief, a payout number changed in the last 7 days, does not apply yet because a member's payout number is her verified Novi number, which cannot be changed in the app.

### D49. Novi instructs, the MFI sends, each pot once, to her own number (22 Oct 2026)
Novi never holds or moves the money (D2): it sends the MFI an instruction (the group's account, the amount, her verified number and her mobile money service), and the MFI sends the pot. Each round has one payout row, claimed before the MFI is called, so two runs of the job at the same moment cannot both instruct it; the MFI treats the same payout ID as the same transfer, and only a failed transfer is attempted again. A transfer the MFI accepts for later is checked on the next run. When the MFI confirms, one PAYOUT line is added to the ledger (D46) and she receives an SMS. When every round has been paid out, the group becomes COMPLETED, which is what lets its members start a third group (D27). To send a pot the MFI must receive the receiving member's number: the one personal detail it is given, and only for that purpose (D33). The job runs every minute while the API is up.

## Sprint 6: The savings record (ACEV)

### D50. The savings record is facts, signed by Novi, shared as a code she hands over (22 Oct 2026)
The record (ACEV) shows facts taken from the ledger (D46), never a score: since when she is a member, how many groups she joined and completed, how many payments she made, how many were on time (paid on or before the due date), late or missed (a past due date with no payment), how much she saved and how many pots she received. Only she sees it. To show it to a lender, she creates a share: a snapshot of the record, signed by Novi with an Ed25519 key, shown on her phone as a QR code. The lender scans it and opens a page served by Novi, in French and English, which checks the signature and says whether the record is valid, expired (after 30 days), withdrawn by her, or changed since it was signed. She can withdraw a share at any time and sees how many times it was opened and when (D37). The public key is published at /v1/verify/public-key, so a lender can check a record without trusting Novi's page. Considered: a credit score (rejected: a number hides how it was made, and a lender in Lomé can read eight facts); a PDF only (deferred: a PDF can be edited, while the signed share cannot, so a PDF will come later as a printed copy of a share). Limitation: until lenders have Novi accounts (Sprint 5), the share is not tied to a named lender as D37 asks; whoever holds the code can open it, which is why it expires, can be withdrawn and logs each view. The signing key is kept in the API's environment (ACEV_PRIVATE_KEY) and must never be committed.

## Sprint 5: MFI console

### D52. MFI staff log in with email, password and an authenticator code, in a world apart from members (23 Oct 2026)
A partner MFI's officers use a web console, not the member app. Each staff account belongs to one MFI and sees only that MFI's groups. Logging in needs three things at once: email, password and the 6-digit code from an authenticator app (time-based codes, RFC 6238, written with Node's crypto). Any wrong part gives the same answer, so a failed login never says which part was wrong; 5 failures lock the account for 15 minutes; each code works only once. A console session lasts 8 hours (a working day) with no refresh token, and logout ends it at once. Staff tokens have their own audience, so a staff token never opens a member route and a member token never opens the console. Accounts are created with a script (npm run staff:create), which shows a one-time password and the authenticator key once. Reason: an officer can see money totals for many groups and act on payouts, so a stolen password alone must not be enough. Considered: SMS codes for staff (rejected: an SMS code can be taken by someone who gets the number moved to a new SIM card, and staff work at a desk with a computer); sharing the member login (rejected: different people, different risks, different rules). Limitations: the authenticator secret is stored as is in the database and should be encrypted with a key kept outside it before real use; staff cannot yet change their password or reset their authenticator themselves.

### D53. An officer sees a held pot but cannot release it short (23 Oct 2026)
A pot held because it is not full (D48) appears in the console with how many payments are missing and since when, but not who is missing (D33). The officer cannot send it short: following up a late payment stays within the group, as in a tontine, and the pot leaves on its own as soon as the last payment arrives. The officer can retry a transfer that failed (D49), since that is the MFI's own operation. Considered: letting the officer release a held pot short, for example if a member is ill (rejected: it breaks D48, the receiving member gets less without the group agreeing, and the MFI would be judging members' situations).

### D54. She can share her record with one MFI by name, seen only in its console (23 Oct 2026)
Answers the limitation in D50. When she shares her savings record, she can choose a partner MFI (for example FUCEC-Togo) instead of creating a QR code. A record shared by name shows nothing on the public page, even to someone holding its code: only that it was shared with FUCEC-Togo. FUCEC's staff, logged in to the console (D52), see it in their list and can open it; another MFI's staff get 404. Each opening is logged with the officer who opened it, and she sees how many times it was opened. Like any share, it lasts 30 days and she can withdraw it, after which it leaves the console list. The QR code for any lender stays as a second choice, for lenders that are not Novi partners. Limitation: the signature covers the facts, not the name of the MFI they were shared with, which is stored beside them; changing it would need access to Novi's database.

### D55. The console is a small web app, French first, with no design kit (23 Oct 2026)
Officers work at a desk in the agency, so the console is a web page, not a phone app: React with Vite in apps/console, sharing the API's types through @novi/shared. It is in French first (the working language of Togo's MFIs), with English one click away. It uses no component library or template: its own styles, the member app's indigo and saffron on an unbleached-cotton background, a wax-print style band, numbers before words, and each round drawn as a pot that fills as payments arrive. In development Vite passes /v1 requests to the API, so the API needs no cross-origin settings; how it is served in production is decided at deployment. The officer's token is kept in the browser tab's sessionStorage, so closing the tab ends the session on a shared computer. Considered: a page served by the API like the verify page (rejected: the console has several screens and actions, which a small app handles more simply); a ready-made admin template (rejected: looks generic, adds weight, and goes against the UX direction).

## Experience

### D56. Numbers and pictures before words; celebrate progress, never compare (25 Oct 2026)
After testing on her phone, the member app had too much explanatory text for traders who scan rather than read, and felt flat. The app now shows, for each running group: the round's pot as a clay jar that fills as members pay, the amount she owes in large figures or a check once paid, a countdown to her own turn, and her on-time streak as a string of beads. A payment that goes through drops three coins into the pot. Her savings record shows three milestones as medallions (first payment, first pot, full cycle), with the ones not yet reached as outlines. Each group carries its own wax-print style band, drawn from its ID, so she recognises it at a glance. Explanations are cut to one line; the rest is in Listen. All drawings are made for Novi with react-native-svg (no emoji, no icon pack), on an unbleached-cotton background with the app's existing indigo and saffron, plus laterite for patterns only. Rule: progress is celebrated for her alone; nothing ranks members or shows the group who is late (D33, D43). Considered: points and leaderboards (rejected: they turn a tontine's trust into competition and shame members in a slow market week); flame or trophy emoji (rejected: generic and not rooted in the context).

### D57. Two reminders by SMS, in daytime only (25 Oct 2026)
A member who has not paid gets an SMS the day before a due date and another on the morning of it, in her language, with the group, the amount and the date. SMS rather than a phone notification, because it reaches basic phones and phones without data. Nothing is sent before 08:00 or after 19:00 in Lomé (GMT all year), and each reminder is recorded, so it goes out once however often the job runs. A member who has paid, or whose payment is on its way, gets nothing. Considered: one reminder only (kept two: market days are busy, and the morning text is the one that prompts payment); push notifications (later, as an addition for smartphones).

## Deployment

### D58. One server on Railway, built from a Dockerfile, serving the API and the console (25 Oct 2026)
Novi goes online early, before real users test it, so problems that only appear on a host show up while the app is small. The API and the MFI console run as one service on Railway with a managed PostgreSQL database; the console's built files are served by the API at /console, from the same address, so no cross-origin settings are needed. The image is built from a Dockerfile (Node 24, OpenSSL for Prisma), which makes the build the same on any host; each start applies pending migrations, and Railway checks /health. Behind Railway's proxy the API trusts one proxy hop, so per-address rate limits see each member's real address. Secrets are typed into Railway's variables, never committed, and are new values, not the ones used on the laptop. The phone app is not part of the server: in development it stays in Expo Go and points at the public address. Considered: Railway's automatic build without a Dockerfile (rejected: less predictable for an npm workspace with Prisma); a separate host for the console (rejected: a second service and cross-origin settings for no gain). Limitation: SMS, identity, MFI and payments are still mock providers online (D3), so codes appear in the server logs; real users need at least real SMS and a pilot sign-up mode first.

### D59. Novi runs on Microsoft Azure, with student credit (25 Oct 2026)
Refines the host in D58: Railway was not accepting new accounts on 25 October. The same Docker image runs on Azure App Service (Linux, Basic B1 with Always on, so the payout and reminder jobs keep running) with Azure Database for PostgreSQL (flexible server, Burstable B1ms, SSL required), paid by the Azure for Students credit. GitHub Actions builds the image on every push to main, stores it in GitHub's container registry and points the web app at it; the container applies migrations on start, as in D58. Considered: Render's free plan (rejected for real users: it sleeps, which stops the background jobs, and its free database is time-limited); Google Cloud Run (rejected: it scales to zero between requests, which also stops the jobs); AWS (more networking and permission work for the same result). The Dockerfile keeps Novi portable: railway.json and render.yaml stay in the repository as alternatives.

### D60. Novi runs on Render's smallest paid plans (25 Oct 2026)
Supersedes D59. Azure for Students could not be activated on this account ("not eligible to renew"), and Railway was still closed to new accounts. Novi runs on Render: the same Docker image on the smallest paid web instance (about 7 USD a month, 512 MB, never sleeps, so the payout and reminder jobs keep running) and the smallest paid PostgreSQL (about 6 USD a month, plus 5 GB of storage at 0.30 USD per GB), both in Frankfurt, Render's closest region to Lome, described in render.yaml. Considered: Render's free plan (rejected: it sleeps, which stops the jobs, before real users test); AWS Lightsail (about 25 USD a month after a 3-month free period, more setup); Azure without the student credit (no advantage over Render at a higher setup cost). The Azure workflow and the Railway settings were removed; the Dockerfile keeps Novi portable to any host.

### D61. The online pilot shows one-time codes in the app (25 Oct 2026)
While SMS is still a mock, testers could not receive their sign-up, identity or new-phone codes: they only appeared in the server logs. Real SMS to Togo through Twilio costs about 0.49 USD per message (Twilio's Togo price list, Oct 2026), so about 100 USD for twenty testers. With PILOT_SHOW_CODES set to "true" (only in render.yaml), the API returns the code that was "sent" and the app shows it on the code screen, labelled "Pilot: this code normally arrives by SMS". The SMS flow itself is unchanged and stays behind its provider interface (D3). Trade-off: anyone holding a tester's phone number could sign up as them, which is acceptable for a closed pilot with demo identities and must be switched off before real use. A local provider (for example Africa's Talking, whose sandbox simulates SMS for free) is the next step.

### D62. A demonstration command pays out a pot before its due date (25 Oct 2026)
Pots leave on their round's due date (D34), so a payout could not be shown during a test or the defence without waiting for that day. `npm run demo:payout -- "Group name"`, run only from the server's shell, runs the normal payout service for that group's next round as if today were its due date. Every other rule still applies: the pot is held unless everyone has paid, goes only to the member whose turn it is, to her own number, once (D49). It is not reachable from the app or the console, so no member or officer can move a pot early.

### D63. A pot leaves only when the MFI officer releases it, and its member confirms receipt (25 Oct 2026)
Until now a full pot was sent automatically on its due date. Two people now take part, as in any financial control. On the due date a full pot becomes READY and appears in the MFI console; the officer checks it and presses "Release the pot", which Novi logs with her name, and only then is the MFI instructed to send it. Once the MFI confirms the transfer, the member whose turn it was answers "I received it" or "It has not arrived"; a "not arrived" answer appears in the console as a dispute for the officer. Novi still never holds the money (D2): the officer acts in the MFI's own console. A transfer that was released and then refused is still retried automatically (D49), and a held pot (D48) becomes ready as soon as it is full. Trade-off: a pot can leave later than its due date if no officer is at the console; reminders to the officer are a later step. The record (ACEV) can now distinguish pots confirmed by the member who received them.

### D64. Sandbox payments go through FedaPay's payment page, confirmed by its signed webhook (26 Oct 2026)
A probe of every "send now" variant (npm run fedapay:probe, 26 Oct) showed that this FedaPay sandbox account answers "Opération non autorisée" to /moov, /mtn and /mtn_open, and 404 to every other form, with both 8- and 10-digit Benin test numbers: sending a request straight to a phone is not enabled for the account. FedaPay's sandbox publishes test numbers for Benin only (MTN 66000001, Moov 64000001). Novi therefore uses FedaPay's hosted payment page in the sandbox: the API creates the transaction and its token, the app opens the page, she pays there with a test number, and FedaPay notifies Novi through the signed webhook; Novi then reads the true status back from FedaPay before crediting anything (D45). The flow is the same in live mode with Togolese operators, once FedaPay enables the account. Tested end to end on 27 Oct: the page succeeds with "Momo Test" and the number in Benin's 10-digit format, 0166000001 (Benin moved to 10 digits in 2024); the 8-digit 66000001 from FedaPay's documentation fails. Until then the pilot can stay on the mock provider, and the FedaPay flow is shown with a test number.

### D65. The ACEV is a signed one-page document with a fingerprint of the ledger (27 Oct 2026)
The shared record was a list of numbers on a plain page. A loan officer needs something she can file: the ACEV is now an A4 attestation with a number (ACEV- plus the share code), the holder's ID-checked name, the MFI that held the funds, four headline facts (share of payments on time, amount saved, pots received and how many their receiver confirmed, completed cycles), the groups, the method in plain words, and a verification block: the QR code, the Ed25519 signature's public key, and a SHA-256 fingerprint of her ledger lines up to the issue date. The fingerprint is inside the signed record, so it ties the attestation to the exact ledger it summarises; the database refuses any change to a ledger line (D46). The lender who scans the QR code and the MFI officer in the console see the same document, which prints or saves as PDF from the browser. Still facts only, no score (D33). Records shared before this date simply lack the new facts.

### D66. The MFI validates each group before its account opens (27 Oct 2026)
Until now, when the organiser pressed "Start", Novi asked the MFI to open the group's account at once. The MFI holds the money and carries the customer due diligence under BCEAO Instruction n°003-03-2025, so it should decide. With MFI_GROUP_APPROVAL set (on Render), a started group waits in STARTING and appears in the console under "Groups to validate", with its contribution, rhythm and size; the officer validates it, and only then is the account opened and the first round scheduled, or declines it with a reason, and the group is cancelled before any money has moved. Both actions are logged with the officer's name. What exactly an officer must check before validating (and whether she needs the members' names, which D33 withholds today) is a question for the MFI interview.

### D67. The console shows the MFI's portfolio over time and what its officers did (27 Oct 2026)
An analytics page gives, over eight weeks, the money collected and paid out per week, the share of payments made on time, the number of members, the groups by state, the pots paid out and how many their receiver confirmed or disputed (D63), and the median time a due pot waited for the officer's release. All figures are totals: no member's name (D33). A log lists every action by the MFI's officers, newest first: groups validated or declined, pots released, transfers retried, and ACEVs opened, with who and when. This is the trail an auditor or the BCEAO's supervisors would ask for, and it lets a branch manager see that pots are released on time.

### D68. A solidarity reserve, pooled across the MFI's groups, pays a late member's share (27 Oct 2026)
When a member had not paid by the due date, her group's pot was held (D48) and the member whose turn it was waited, often for a temporary difficulty of a few weeks, which is how most late payments happen. Now 2% of every contribution is set aside (100 FCFA of 5 000; the member still pays 5 000, and a pot of three is 3 x 4 900). The shares of all the groups at one MFI form one solidarity fund held at the MFI: a single group's reserve, a few hundred francs, could never cover a whole share, while the pooled fund can from the first round. On the due date, if the fund holds enough, it pays every missing share, the pot becomes ready to release complete and on time, and each covered member owes her share; her late payment refills the fund. At the end of the cycle, what the group put in, less what its own members still owe, goes back through the MFI to the members who owe nothing, in proportion to what each put in. Each movement is a ledger line (RESERVE_IN, RESERVE_COVER, RESERVE_REPAY, RESERVE_RETURN). A covered round still counts as missed on her ACEV, which also shows how many covers she repaid: the fund protects the group, not the record. The idea of pooling the cover of temporary defaults across many borrowers was put forward by Abdou Sissé on "Déchiffrer l'éco"; whether a fund of this kind needs a specific BCEAO authorisation, and who carries a loss larger than the fund, are questions for the MFI interview.

### D69. Protecting the group: next of kin, death, departure, a lost phone and debt (27 Oct 2026)
A tontine has to survive what happens to its members. In all these cases the money stays in the group's account at the MFI (D2); what changes is who receives it and who may log in, always by the MFI officer at the counter, and every action is logged with the officer's name.
- Next of kin. In Me, a member names the person who receives what she is owed if she dies: name, relation and a Togolese number that is not her own. Home reminds her until she has done it, from her first group or invitation. Novi never contacts this person while she is alive, and her groups do not see who it is.
- Finding a member. The console's Members page finds a member of this MFI's groups by her phone number, with her legal name, next of kin, what she owes the fund, and her seats. It is the one place the console shows a name (an exception to D33), because the officer acts for a person standing in front of her, or on a death certificate; each lookup is logged. A number outside this MFI's groups is answered as unknown.
- Death. On the death certificate, the officer records it. Her account is closed and logged out everywhere. What the fund paid for her is written off, and the fund pays her remaining shares, so nobody else carries them and the others' reserve returns are not reduced: the loss is the pooled fund's (D68), the same logic as the death cover MFIs attach to loans. Her pot, at her turn, and her part of the reserve go to her next of kin's number, or to the heir's number the officer types from the documents. If she was the organiser, the role passes to the next member in the turn order.
- Departure. A member who stops taking part in a started group is recorded as having left. She still owes what the fund pays for her. Before any member's pot is released, what she owes the fund in that group is taken from it first, so nobody can collect the pot and leave her debt behind. If her turn has already passed, the debt stays.
- Debt. While a member owes the fund anything not repaid or written off, she cannot create or join another group (DEBT_OUTSTANDING). One ID-checked account per NIU (D12) means she cannot start again under a new name; recovering a debt after the cycle is the MFI's, as for any of its customers.
- A lost or stolen phone. She comes to the agency with her ID card; the officer records the new number. Every session is closed and every phone she had trusted must pass the SMS code again, now sent to the new number, so whoever holds the old phone is out. Her pots not yet sent follow the new number.
- A new organiser. The officer can name another member organiser, at the organiser's request or after the automatic handover.
Questions for the MFI interview: which documents it requires to pay an heir, and whether a death cover of this kind is allowed from the solidarity fund or needs an insurer.

## Partners, money and data (20 Oct 2026)

### D33. The MFI sees group totals, not individual members; the ACEV is shared only at her request (20 Oct 2026)
The MFI that holds a group's money sees the group's total and the contribution amount set by its rules (for example 10 members x 5 000 FCFA = 50 000 FCFA due on Friday), not which member paid what. The per-member detail stays in Novi's ledger, visible to the group's own members. The MFI may use this data only to hold and pay out the money. A member's ACEV reaches an MFI only when she asks, to apply for credit, one request at a time; each share is recorded. The carnet is never shared by default. Reason: whoever holds the money necessarily sees the money, but traders may not want an institution to see each woman's payments; Ghana's e-levy showed informal workers pull back from tools they perceive as surveillance. To confirm in the MFI interview: whether anti-money-laundering rules require the MFI to identify each contributor, which may require a group account with named signatories rather than totals alone.

### D34. The MFI is invisible infrastructure; Novi orchestrates; the ACEV is portable (20 Oct 2026)
A licensed institution holds each group's money: an MFI partner, which members do not deal with directly. Members sign up, save and see everything in Novi; money screens show one line, "held at" the institution, for transparency. Novi never holds funds: under BCEAO Instruction 001-01-2024, Art. 2, payment services are reserved to banks, credit institutions, payment institutions, microfinance institutions and e-money issuers, and a tontine pot held for days or weeks also resembles savings, which banking and microfinance law reserve to licensed institutions. Considered: Novi collecting into its own FedaPay merchant balance (rejected: Novi would hold members' money without a licence) and members paying each other directly with Novi only recording (rejected: Novi could not run payouts automatically, its first differentiator). The ACEV belongs to the member and can be taken to any lender, not only the custodian (D33). Roadmap: if Novi scales, register under the lighter categories of the same instruction (account aggregation, Art. 3(40) and Art. 9; payment initiation, Art. 30 to 31), subject to legal advice; the instruction allows partnerships and forbids exclusivity (Art. 7), which supports working with several MFIs.

### D35. Identity is checked by scanning the e-ID card's QR code (20 Oct 2026)
Supersedes the typed-details step of D12. At sign-up the member scans the QR code on her e-ID card; Novi verifies ANID's signature on the data offline, which ANID describes as "verifiable offline and free of charge" (ID4Africa 2026), so there is no failed-ID queue for an MFI to handle. The scan proves the card is genuine, not that the person holding the phone owns it: one account per NIU and the SMS code to her phone remain, and the accredited online check through a licensed partner is the route to proving the holder. Until ANID publishes its QR format and signing key, the verifier uses a test key. A fallback is needed for members without a readable e-ID card (damaged card, card not yet issued).

### D36. Novi works with several MFIs, never exclusively (20 Oct 2026)
Each group's money is held by one licensed institution, chosen for the group; Novi can add further MFIs. BCEAO Instruction 001-01-2024, Art. 7, allows service partnerships and forbids exclusivity clauses. A member's ACEV can be taken to any of them.

### D37. Lenders see a member's detailed record only with her approval (20 Oct 2026)
The lender view shows one member's record: her payouts, her contributions, how regularly she paid, and any missed payments, because these inform the decision to grant a loan. It shows nothing until she approves access for a named lender. Each approval is for one lender, lasts a limited time, can be withdrawn, and every view is logged. Without her approval an MFI sees only group totals as custodian (D33). Considered: standing access for the custodian MFI (rejected: it turns the custodian into a monitor of each trader and conflicts with D33).
