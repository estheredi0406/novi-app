# Decision log

Each entry records a choice, why it was made, and what was considered instead. Entries are never rewritten or deleted; a changed decision gets a new entry that names the one it supersedes.

## Sprint 0: Foundations

### D1. One repository for the whole system (13 Oct 2026)
The API, mobile app, mock MFI and shared code live in one npm workspaces repository. The app and API import the same type definitions from packages/shared, so if the shape of a contribution changes on one side, the other fails to compile before the demo, not during it. A feature touching both sides is one commit. Considered: separate repositories; rejected because shared types would have to be published and versioned separately.

### D2. Novi never holds money (13 Oct 2026)
Contributions go to an account at a licensed microfinance institution. Novi keeps the rules and the ledger and instructs the MFI to pay out. Under BCEAO Instruction n°001-01-2024, only banks, microfinance institutions, payment institutions and e-money issuers may provide payment services; Novi holds none of these licences.

### D3. Every outside service sits behind an interface (13 Oct 2026)
Identity checks, payments, the MFI and SMS are reached through IdentityProvider, PaymentProvider, MfiAdapter and SmsProvider. The demo uses mock versions; a real provider replaces one file. Reasons: FedaPay documents sandbox test numbers for Benin only, ANID identity checks are open to partners only, and Africa's Talking does not offer SMS or USSD in Togo in production.

### D4. Money is stored as whole numbers of FCFA (13 Oct 2026)
FCFA is used without a smaller unit in daily trade, and decimal numbers in JavaScript cause rounding errors (0.1 + 0.2 gives 0.30000000000000004). Every amount is an integer number of FCFA.

### D5. The ledger is append-only (13 Oct 2026)
A ledger entry is never edited or deleted; a correction is a new entry that references the one it corrects. Every member can then trust that the history she sees is the history that happened, which answers the trust problem behind organiser fraud in tontines.

### D6. Node.js 24 (13 Oct 2026)
Supersedes the Node 20 choice in the original build brief. Node 20 reached end of life on 30 April 2026 and no longer receives security fixes (nodejs.org/en/about/previous-releases); Node 24 is the current long-term support line. Pinned in .nvmrc and in the engines field of package.json so development and hosting run the same version.

### D7. Local database for development; Railway for deployment only (13 Oct 2026)
PostgreSQL runs on the developer's laptop during Sprints 0 to 8; Railway hosts the API and database from Sprint 9, with one trial deployment of the API at the end of Sprint 0 to prove the pipeline. Railway's Free plan gives $1 of credit per month and its Hobby plan costs $5 per month (docs.railway.com/pricing), which would not keep an API and a database running continuously while no users exist; trial databases are deleted 30 days after credits expire. A local database also works offline. Moving changes only DATABASE_URL.

### D8. PostgreSQL 18 with a dedicated, limited user (13 Oct 2026)
Development uses PostgreSQL 18 on port 5432. The API connects as novi_app, which owns only the novi_dev database, never as the postgres administrator (least privilege). novi_app has CREATEDB because Prisma creates a temporary shadow database to check each migration.

### D9. Prisma ORM 7.10.0, pinned exactly (13 Oct 2026)
On 13 Oct 2026 the npm registry tagged prisma 8.0.0-rc.22 (a release candidate) as latest, with stable 7.10.0 under the prev tag. Novi uses the stable line. prisma, @prisma/client and @prisma/adapter-pg are installed with exact versions because they must always match. The generated client is written to apps/api/src/generated so it stays inside the TypeScript rootDir, and is ignored by Git because prisma generate rebuilds it.

### D10. Expo SDK 57, blank template, Expo Go until native modules are needed (14 Oct 2026)
The mobile app starts from Expo's blank TypeScript template so every file is written and explained by the author. It runs in Expo Go during development; a development build replaces it when a feature needs native code Expo Go lacks (WatermelonDB, Sprint 6). No web target: Novi's users are on phones, and the MFI console is a separate web project.

### D11. Known npm audit warnings deferred to the security pass (14 Oct 2026)
create-expo-app reported 22 vulnerabilities, mostly in development tooling. npm audit fix --force is not used because it upgrades packages beyond the versions Expo SDK 57 supports. They are reviewed in Sprint 9 with npm audit --omit=dev, which lists only issues in shipped code.

## Sprint 1: Sign-up and login

### D12. Identity is verified before an account exists (14 Oct 2026)
Under BCEAO Instruction 003-03-2025, Art. 14(5), a remote client's first transaction may only happen after her identity is verified. At sign-up, after consenting, the member enters her NIU, full name and date of birth; the mock ANID service checks they match its record and sends a one-time code to the phone on ANID's record, as MOSIP-based systems do. Names are compared ignoring capitals and extra spaces; everything else must match exactly. After 3 failed attempts the NIU is blocked for 24 hours and she is told to visit the MFI with her ID card. No account is created until verification succeeds, so there is no unverified account state and no ID queue for MFI officers. Supersedes the build brief's "accept invitations but cannot pay" state. Known limitation: the phone on ANID's record may not be hers today; the branch fallback covers this.

### D13. Women traders first, open to every informal trader (14 Oct 2026)
Novi is designed around informal women traders, the group most affected by the problem: women hold 69.7% of jobs in Togo's informal units (INSEED & AFRISTAT, ERI-ESI 2017) and 45.4% of women own a financial account against 70.0% of men (Global Findex 2024). It starts in Lomé's markets but serves any informal trader: informal work extends well beyond markets (91.6% of jobs in Togo are informal, same survey), and nothing excludes men. A member records the neighbourhood where she trades (required, never an exact location) and a market only if she trades in one. Novi stores no gender: the product does not need it, and the women focus is measured in the research, not in the database. Interface text uses neutral wording, including in gendered languages such as French.

### D14. Secrets live only in environment files (14 Oct 2026)
The database address, JWT_SECRET and NIU_HASH_KEY are read from apps/api/.env (and .env.test for tests), which Git ignores; the API refuses to start if one is missing. .env.example holds placeholders only, so another developer knows what to set without seeing real values. On 16 Oct 2026 the real local password was found in .env.example; it was replaced with a placeholder and both database passwords were changed, because Git history keeps the old value. Every commit is now checked with git diff --staged first.

### D15. Two names: legal name and display name (14 Oct 2026)
legalName comes from the ANID check, appears on the ACEV and cannot be changed in the app. displayName is chosen by the member and is what her group sees. Groups never see the legal name or phone number.

### D16. Easy PINs are refused (14 Oct 2026)
A PIN made of one repeated digit, a straight sequence in either direction, or one of the most common choices is refused, on the phone at once and by the API with PIN_TOO_WEAK. The rule lives in packages/shared so app and API apply exactly the same one.

### D17. No fingerprint or face unlock (14 Oct 2026)
Phones in Lomé are often shared within a family. Device biometrics trust every fingerprint or face enrolled on the phone, which may include someone else's, so Novi relies on the PIN only she knows.

### D18. PIN lockout grows with each lock (14 Oct 2026)
Five wrong PINs lock the account for 15 minutes, then 1 hour, then 24 hours. A right PIN resets the count and the escalation. The lock is checked on the server, so reinstalling the app does not lift it.

### D19. Short access tokens, rotated refresh tokens, a session check on every request (15 Oct 2026)
Access tokens last 15 minutes. Refresh tokens last 30 days, are stored only as SHA-256 hashes and work once: each use returns a new pair. A retired refresh token presented again after a 30-second grace (for weak connections that send twice) revokes every session of that member. Every request also checks that its session is still open, so logout and PIN reset take effect at once.

### D20. Forgotten PIN is reset by SMS and logs out every phone (15 Oct 2026)
A PIN reset needs the SMS code for her number, then a new PIN typed twice. It revokes all sessions, clears any lockout, and records pinChangedAt so a reset stamp issued earlier cannot be used again.

### D21. Expo Router and Noto fonts (15 Oct 2026)
Screens use Expo Router (file-based routes, typed routes). Noto Sans and Noto Sans Display are loaded before anything is shown, because they contain the Ewe letters (ɖ ƒ ɣ ŋ ɔ ɛ ʋ) that system fonts may lack.

### D22. Interface text as translation keys (15 Oct 2026)
All text lives in en.json, fr.json and ee.json, read with i18next. The API sends message keys, never sentences. French must contain every English key (checked at compile time); Ewe falls back to French until a native speaker has reviewed it. A compile-time check fails if the API can send an error key that has no English text.

### D23. PIN at every opening; one session per phone (15 Oct 2026)
Tokens are cleared each time the app starts, so Novi asks for the PIN at every opening; only her phone number and display name stay on the phone, in secure storage. Logging in on a phone closes that phone's previous session (reason REPLACED).

### D24. Sign-up protections (16 Oct 2026)
Sign-up answers the same whether or not a number already has an account: the SMS to a registered number says so instead of carrying a code, and nothing on screen reveals it. Codes are limited per phone (60 seconds apart, 5 per hour, counted in the database) and per address (in memory). Identity checks are limited to 3 failures per NIU in 24 hours. The sign-up draft (stamps and PIN) is kept in memory only and is lost if the app closes.

### D25. Multi-step login and PIN reset live in one screen each (16 Oct 2026)
Login (PIN, lockout countdown, new-phone code) and PIN reset (phone, code, new PIN) are each one screen with steps, not one screen per step. The PIN typed before a new-phone check, and the stamp from the reset SMS, stay in that screen's memory only: never in storage, never in the route address, and gone when the screen closes. Sign-up keeps separate screens because its steps are long and each one is checked by the API before the next.

## Sprint 2: Groups and rules

### D26. A group counts towards the 3-group limit from the moment she accepts its rules (16 Oct 2026)
A group counts towards a member's "at most 3 active groups" while it is PROPOSED (and she has accepted), STARTING or ACTIVE, not only once it is ACTIVE. Otherwise a member could accept many groups at once, and when they all start she could not pay into all of them, so each group would fail for everyone else in it.

### D27. "One completed cycle" means a group she belonged to reached COMPLETED (16 Oct 2026)
A member may start 2 groups. To start a third, she must have been a member of a group that reached COMPLETED: she kept paying until every member had received the pot. Receiving her own pot once is not enough, because she could stop paying straight after her turn.

### D28. A group has between 3 and 15 members (16 Oct 2026)
With 2 members a group is a private arrangement, and one missed payment empties half the pot. 15 is the upper limit already set by the product rules.

### D29. Rules are versioned; a group starts only when every seat accepted the current version (16 Oct 2026)
Each change to a group's rules (amount, frequency, size, payout order) creates a new version, and every acceptance falls back to "not yet". The organiser can start the group only when every remaining seat has accepted the current version. Silent seats must be removed first, which changes the size and therefore creates a new version that everyone accepts again. This proves later that every member agreed to the exact rules her money followed.

### D30. Groups pay weekly or monthly, on a fixed day (16 Oct 2026)
A group's rules set WEEKLY (day 1 Monday to 7 Sunday) or MONTHLY (day 1 to 28). Weekly matches market-day tontines; monthly suits members paid by the month. Monthly days stop at 28 so every month has the due day.

### D31. Contributions are between 100 and 1 000 000 FCFA (16 Oct 2026)
A group's contribution must be a whole number of FCFA from 100 to 1 000 000. The bounds are a safety net against typing mistakes (50 000 000 instead of 5 000), not a product rule; they are deliberately wide and will be confirmed with the partner MFI.

### D32. Zod checks the shape of a request; the rules engine checks the rules (16 Oct 2026)
Routes use Zod only to check that the right kinds of values were sent (a number, one of WEEKLY or MONTHLY) and to refuse unknown fields. Whether a value is allowed (3 to 15 members, 100 to 1 000 000 FCFA) is decided only by groupRules.ts, so each rule lives in one place and always answers with the same error code. A person with no seat in a group is told the group does not exist (404), not that access is forbidden, so group IDs cannot be probed.

### D38. Invitations go to a phone number; a seat exists only once she answers (20 Oct 2026)
The organiser invites by phone number. The invitation holds a place in the group (it counts towards the size) but is not a seat: the person gets a seat only when she answers. Inviting works, and looks, the same whether or not the number has a Novi account: the SMS text is the same, and the group sees only a masked number ("+228 90 •• •• 56") until she answers, so the organiser cannot use invitations to find out who uses Novi (the same rule as login, D24). A number invited before it had an account sees the invitation as soon as it signs up, because invitations are found by her verified phone number. The organiser can withdraw an invitation or remove a seat before the group starts; her own seat cannot be removed (she cancels the group instead).

### D39. Answering a group: accept, ask for a change, or say no (20 Oct 2026)
She accepts or asks for a change only once the organiser has proposed the group, and her answer carries the version of the rules she read: if the organiser changed them meanwhile, the answer is refused (RULES_CHANGED) and she reads the new version (D29). Accepting checks her 3-group limit (D26). Asking for a change keeps her place and shows her note to the group; the organiser answers by changing the rules (everyone answers again) or by removing her seat. She can say no at any point before the group starts, including while it is a draft and after she accepted; her place is freed and the group never sees her name, so saying no costs her nothing with the organiser. Her seat is created from the invitation the first time she answers (D38). The organiser does not answer her own group: proposing it is her acceptance, cancelling it is her way out.

### D40. No group search or discovery: a group is reached only by invitation (20 Oct 2026)
There is no list of open groups, no search bar for groups or members, and no "groups near you", even at market level. A person learns that a group exists only when its organiser invites her phone number (D38), and a group's page answers 404 to anyone without a seat or a pending invitation (D32). Reason: a list of groups shows who saves, how much, how often and in which market, which tells a thief or a jealous relative where cash gathers on which day, and tells others who is in which group; tontines in Lomé are formed between people who already trust each other, so discovery adds risk without matching how groups form. Supersedes "market-level discovery" and "invite by search" in the brief (F6 is now: invite by phone number; answer). The profile's area and market are kept for the research and for matching a group to an MFI branch; nothing shows them to other members.

### D41. Payout order: drawn once by Novi, or fixed by the organiser and accepted by everyone (20 Oct 2026)
A group's rules say DRAWN (the default) or FIXED. DRAWN: Novi draws the order when the group starts, with Fisher-Yates and the operating system's secure random numbers (Node.js crypto.randomInt), so every order is equally likely and nobody, Novi included, can steer it; the draw happens once and is recorded in the audit trail, and a retry never draws again, so nobody can retry until the draw suits them. FIXED: once every seat is taken, the organiser sets who is paid first, second and so on (for example Abla first because her shop rent is due); the order is saved as a new version of the rules, so every member accepts the exact order before the group can start (D29). The order must name every member once, and is checked again at the start in case someone left. Considered: paying in the order members accepted (rejected: it rewards speed, not need, and late answerers always go last).

### D42. Starting a group: Novi checks and fixes the order, then the MFI opens the account (20 Oct 2026)
The organiser starts the group. Novi checks every rule (every seat accepted the current version, D29; her start limit, D27), fixes the payout order and moves the group to STARTING, from which nobody can leave or change anything. Novi then asks the MFI to open the group's account and, once it answers, the group is ACTIVE. The MFI is told the group's totals only (contribution, number of members, frequency), never names or phone numbers (D33). If the MFI does not answer, the group waits in STARTING with its order kept, and the organiser can try again; Novi sends its own group ID with each request so a retry never opens a second account. The database is never kept waiting on the MFI: the two steps are separate transactions. The MFI sits behind an MfiAdapter interface with a mock until a partner offers an API (D3).

### D43. Guarding against a wrong number: four checks before the wrong person can join (20 Oct 2026)
A typo in an invited number could let a stranger accept, receive a pot and stop paying, the classic tontine loss. Four checks: (1) before the SMS is sent, the organiser sees the whole number she typed and confirms it; (2) the invitation screen tells the invited person to accept only if she knows the organiser, and to say no if the invitation reached her by mistake; (3) before the start, the organiser is shown every member's name and asked whether she knows each of them in person; (4) the organiser, and only she, sees part of each member's number next to her name ("Abla, +228 90 •• •• 02"), so she can check that the person who accepted is the number she meant. Showing the organiser 4 digits of a number she typed herself reveals nothing new; other members still see names only (D15). Until the start, the organiser can remove anyone (D38). Considered: showing the organiser the invited person's legal name (rejected: it would reveal an ANID name before the person agreed to join, against D15 and D38).

## Sprint 3: Money in

### D44. The calendar: round 1 is due on the first due day after the start (21 Oct 2026)
When the group becomes ACTIVE, Novi writes one round per member. Round N is paid out to the member whose payout position is N (D41), and is due on the Nth due day after the start: never the start day itself, so nobody is asked to pay within hours of the start, and the MFI has time to open the account. Weekly rounds are 7 days apart, monthly ones on the same day each month (days stop at 28, D30). Dates are calendar days in UTC, because Togo uses GMT all year with no summer time. A round can be paid from the day after the previous round's due date; earlier rounds can still be paid late, later ones not yet.

### D45. A payment is credited once, only after the provider confirms it (21 Oct 2026)
She taps Pay; Novi asks the payment provider to send a request to her own verified number (never another wallet), and she confirms on her phone with her mobile money PIN, which Novi never sees. The payment counts only when the provider says the money moved. Each webhook is checked: its signature (HMAC-SHA256, header X-FEDAPAY-SIGNATURE, older than 5 minutes refused, as in FedaPay's own library); the same delivery twice is recognised by a hash of its body; and its content is not trusted, so Novi asks the provider for the transaction's status, as FedaPay advises. A payment whose amount differs from the contribution is not credited and is flagged for the MFI officer. Crediting is idempotent: the update to PAID only matches a payment not yet PAID, and the ledger accepts one line per payment. If a webhook is lost, her "check" asks the provider directly. One request per round at a time; a new one after 5 minutes or a failure.

### D46. The ledger is append-only in the database itself (21 Oct 2026)
D5 is enforced by PostgreSQL, not only by the code: a trigger on ledger_entries refuses every UPDATE and DELETE, so neither a bug nor anyone using the app's database account can change history. A mistake is fixed by adding a CORRECTION line that points to the line it corrects. Payment requests (contributions) are a separate table that does change (PENDING, then PAID or FAILED), because a request is not money; only a confirmed payment becomes a ledger line.

### D47. FedaPay is called directly, not through its Node library (21 Oct 2026)
FedaPay's official Node library (fedapay 1.2.5) depends on axios 0.28, for which npm audit reports several high-severity advisories. Novi calls FedaPay's REST API with Node's built-in fetch instead (create the transaction, get a token, "send now" with mode moov_tg or togocel, read the status back), using the request and response shapes from the library's own tests. The adapter sits behind PaymentProvider (D3) and is selected with PAYMENT_PROVIDER=fedapay; it has not yet been run against the sandbox, which needs a FedaPay account and keys. Tests and the laptop use a mock that signs its webhooks the same way.

## Sprint 4: Money out

### D48. A pot is sent on its due date, and only when it is full (22 Oct 2026)
On a round's due date Novi instructs the MFI to send the pot to the member whose turn it is. Before the due date nothing is sent, even if everyone has paid early: members expect the pot on the agreed day. If the day has passed and someone has not paid, the payout is HELD, never sent short, and every member sees "Pot held: waiting for 1 payment". The moment the last payment is confirmed, the held pot is released without waiting for the next run of the payout job. Considered: paying out a partial pot on time (rejected: the member whose turn it is would be short-changed by someone else's lateness, and the group would owe her the rest); a further hold rule from the brief, a payout number changed in the last 7 days, does not apply yet because a member's payout number is her verified Novi number, which cannot be changed in the app.

### D49. Novi instructs, the MFI sends, each pot once, to her own number (22 Oct 2026)
Novi never holds or moves the money (D2): it sends the MFI an instruction (the group's account, the amount, her verified number and her mobile money service), and the MFI sends the pot. Each round has one payout row, claimed before the MFI is called, so two runs of the job at the same moment cannot both instruct it; the MFI treats the same payout ID as the same transfer, and only a failed transfer is attempted again. A transfer the MFI accepts for later is checked on the next run. When the MFI confirms, one PAYOUT line is added to the ledger (D46) and she receives an SMS. When every round has been paid out, the group becomes COMPLETED, which is what lets its members start a third group (D27). To send a pot the MFI must receive the receiving member's number: the one personal detail it is given, and only for that purpose (D33). The job runs every minute while the API is up.

## Sprint 6: The savings record (ACEV)

### D50. The savings record is facts, signed by Novi, shared as a code she hands over (22 Oct 2026)
The record (ACEV) shows facts taken from the ledger (D46), never a score: since when she is a member, how many groups she joined and completed, how many payments she made, how many were on time (paid on or before the due date), late or missed (a past due date with no payment), how much she saved and how many pots she received. Only she sees it. To show it to a lender, she creates a share: a snapshot of the record, signed by Novi with an Ed25519 key, shown on her phone as a QR code. The lender scans it and opens a page served by Novi, in French and English, which checks the signature and says whether the record is valid, expired (after 30 days), withdrawn by her, or changed since it was signed. She can withdraw a share at any time and sees how many times it was opened and when (D37). The public key is published at /v1/verify/public-key, so a lender can check a record without trusting Novi's page. Considered: a credit score (rejected: a number hides how it was made, and a lender in Lomé can read eight facts); a PDF only (deferred: a PDF can be edited, while the signed share cannot, so a PDF will come later as a printed copy of a share). Limitation: until lenders have Novi accounts (Sprint 5), the share is not tied to a named lender as D37 asks; whoever holds the code can open it, which is why it expires, can be withdrawn and logs each view. The signing key is kept in the API's environment (ACEV_PRIVATE_KEY) and must never be committed.

## Sprint 5: MFI console

### D52. MFI staff log in with email, password and an authenticator code, in a world apart from members (23 Oct 2026)
A partner MFI's officers use a web console, not the member app. Each staff account belongs to one MFI and sees only that MFI's groups. Logging in needs three things at once: email, password and the 6-digit code from an authenticator app (time-based codes, RFC 6238, written with Node's crypto). Any wrong part gives the same answer, so a failed login never says which part was wrong; 5 failures lock the account for 15 minutes; each code works only once. A console session lasts 8 hours (a working day) with no refresh token, and logout ends it at once. Staff tokens have their own audience, so a staff token never opens a member route and a member token never opens the console. Accounts are created with a script (npm run staff:create), which shows a one-time password and the authenticator key once. Reason: an officer can see money totals for many groups and act on payouts, so a stolen password alone must not be enough. Considered: SMS codes for staff (rejected: an SMS code can be taken by someone who gets the number moved to a new SIM card, and staff work at a desk with a computer); sharing the member login (rejected: different people, different risks, different rules). Limitations: the authenticator secret is stored as is in the database and should be encrypted with a key kept outside it before real use; staff cannot yet change their password or reset their authenticator themselves.

### D53. An officer sees a held pot but cannot release it short (23 Oct 2026)
A pot held because it is not full (D48) appears in the console with how many payments are missing and since when, but not who is missing (D33). The officer cannot send it short: following up a late payment stays within the group, as in a tontine, and the pot leaves on its own as soon as the last payment arrives. The officer can retry a transfer that failed (D49), since that is the MFI's own operation. Considered: letting the officer release a held pot short, for example if a member is ill (rejected: it breaks D48, the receiving member gets less without the group agreeing, and the MFI would be judging members' situations).

### D54. She can share her record with one MFI by name, seen only in its console (23 Oct 2026)
Answers the limitation in D50. When she shares her savings record, she can choose a partner MFI (for example FUCEC-Togo) instead of creating a QR code. A record shared by name shows nothing on the public page, even to someone holding its code: only that it was shared with FUCEC-Togo. FUCEC's staff, logged in to the console (D52), see it in their list and can open it; another MFI's staff get 404. Each opening is logged with the officer who opened it, and she sees how many times it was opened. Like any share, it lasts 30 days and she can withdraw it, after which it leaves the console list. The QR code for any lender stays as a second choice, for lenders that are not Novi partners. Limitation: the signature covers the facts, not the name of the MFI they were shared with, which is stored beside them; changing it would need access to Novi's database.

### D55. The console is a small web app, French first, with no design kit (23 Oct 2026)
Officers work at a desk in the agency, so the console is a web page, not a phone app: React with Vite in apps/console, sharing the API's types through @novi/shared. It is in French first (the working language of Togo's MFIs), with English one click away. It uses no component library or template: its own styles, the member app's indigo and saffron on an unbleached-cotton background, a wax-print style band, numbers before words, and each round drawn as a pot that fills as payments arrive. In development Vite passes /v1 requests to the API, so the API needs no cross-origin settings; how it is served in production is decided at deployment. The officer's token is kept in the browser tab's sessionStorage, so closing the tab ends the session on a shared computer. Considered: a page served by the API like the verify page (rejected: the console has several screens and actions, which a small app handles more simply); a ready-made admin template (rejected: looks generic, adds weight, and goes against the UX direction).

## Experience

### D56. Numbers and pictures before words; celebrate progress, never compare (25 Oct 2026)
After testing on her phone, the member app had too much explanatory text for traders who scan rather than read, and felt flat. The app now shows, for each running group: the round's pot as a clay jar that fills as members pay, the amount she owes in large figures or a check once paid, a countdown to her own turn, and her on-time streak as a string of beads. A payment that goes through drops three coins into the pot. Her savings record shows three milestones as medallions (first payment, first pot, full cycle), with the ones not yet reached as outlines. Each group carries its own wax-print style band, drawn from its ID, so she recognises it at a glance. Explanations are cut to one line; the rest is in Listen. All drawings are made for Novi with react-native-svg (no emoji, no icon pack), on an unbleached-cotton background with the app's existing indigo and saffron, plus laterite for patterns only. Rule: progress is celebrated for her alone; nothing ranks members or shows the group who is late (D33, D43). Considered: points and leaderboards (rejected: they turn a tontine's trust into competition and shame members in a slow market week); flame or trophy emoji (rejected: generic and not rooted in the context).

### D57. Two reminders by SMS, in daytime only (25 Oct 2026)
A member who has not paid gets an SMS the day before a due date and another on the morning of it, in her language, with the group, the amount and the date. SMS rather than a phone notification, because it reaches basic phones and phones without data. Nothing is sent before 08:00 or after 19:00 in Lomé (GMT all year), and each reminder is recorded, so it goes out once however often the job runs. A member who has paid, or whose payment is on its way, gets nothing. Considered: one reminder only (kept two: market days are busy, and the morning text is the one that prompts payment); push notifications (later, as an addition for smartphones).

## Deployment

### D58. One server on Railway, built from a Dockerfile, serving the API and the console (25 Oct 2026)
Novi goes online early, before real users test it, so problems that only appear on a host show up while the app is small. The API and the MFI console run as one service on Railway with a managed PostgreSQL database; the console's built files are served by the API at /console, from the same address, so no cross-origin settings are needed. The image is built from a Dockerfile (Node 24, OpenSSL for Prisma), which makes the build the same on any host; each start applies pending migrations, and Railway checks /health. Behind Railway's proxy the API trusts one proxy hop, so per-address rate limits see each member's real address. Secrets are typed into Railway's variables, never committed, and are new values, not the ones used on the laptop. The phone app is not part of the server: in development it stays in Expo Go and points at the public address. Considered: Railway's automatic build without a Dockerfile (rejected: less predictable for an npm workspace with Prisma); a separate host for the console (rejected: a second service and cross-origin settings for no gain). Limitation: SMS, identity, MFI and payments are still mock providers online (D3), so codes appear in the server logs; real users need at least real SMS and a pilot sign-up mode first.

### D59. Novi runs on Microsoft Azure, with student credit (25 Oct 2026)
Refines the host in D58: Railway was not accepting new accounts on 25 October. The same Docker image runs on Azure App Service (Linux, Basic B1 with Always on, so the payout and reminder jobs keep running) with Azure Database for PostgreSQL (flexible server, Burstable B1ms, SSL required), paid by the Azure for Students credit. GitHub Actions builds the image on every push to main, stores it in GitHub's container registry and points the web app at it; the container applies migrations on start, as in D58. Considered: Render's free plan (rejected for real users: it sleeps, which stops the background jobs, and its free database is time-limited); Google Cloud Run (rejected: it scales to zero between requests, which also stops the jobs); AWS (more networking and permission work for the same result). The Dockerfile keeps Novi portable: railway.json and render.yaml stay in the repository as alternatives.

### D60. Novi runs on Render's smallest paid plans (25 Oct 2026)
Supersedes D59. Azure for Students could not be activated on this account ("not eligible to renew"), and Railway was still closed to new accounts. Novi runs on Render: the same Docker image on the smallest paid web instance (about 7 USD a month, 512 MB, never sleeps, so the payout and reminder jobs keep running) and the smallest paid PostgreSQL (about 6 USD a month, plus 5 GB of storage at 0.30 USD per GB), both in Frankfurt, Render's closest region to Lome, described in render.yaml. Considered: Render's free plan (rejected: it sleeps, which stops the jobs, before real users test); AWS Lightsail (about 25 USD a month after a 3-month free period, more setup); Azure without the student credit (no advantage over Render at a higher setup cost). The Azure workflow and the Railway settings were removed; the Dockerfile keeps Novi portable to any host.

### D61. The online pilot shows one-time codes in the app (25 Oct 2026)
While SMS is still a mock, testers could not receive their sign-up, identity or new-phone codes: they only appeared in the server logs. Real SMS to Togo through Twilio costs about 0.49 USD per message (Twilio's Togo price list, Oct 2026), so about 100 USD for twenty testers. With PILOT_SHOW_CODES set to "true" (only in render.yaml), the API returns the code that was "sent" and the app shows it on the code screen, labelled "Pilot: this code normally arrives by SMS". The SMS flow itself is unchanged and stays behind its provider interface (D3). Trade-off: anyone holding a tester's phone number could sign up as them, which is acceptable for a closed pilot with demo identities and must be switched off before real use. A local provider (for example Africa's Talking, whose sandbox simulates SMS for free) is the next step.

### D62. A demonstration command pays out a pot before its due date (25 Oct 2026)
Pots leave on their round's due date (D34), so a payout could not be shown during a test or the defence without waiting for that day. `npm run demo:payout -- "Group name"`, run only from the server's shell, runs the normal payout service for that group's next round as if today were its due date. Every other rule still applies: the pot is held unless everyone has paid, goes only to the member whose turn it is, to her own number, once (D49). It is not reachable from the app or the console, so no member or officer can move a pot early.

### D63. A pot leaves only when the MFI officer releases it, and its member confirms receipt (25 Oct 2026)
Until now a full pot was sent automatically on its due date. Two people now take part, as in any financial control. On the due date a full pot becomes READY and appears in the MFI console; the officer checks it and presses "Release the pot", which Novi logs with her name, and only then is the MFI instructed to send it. Once the MFI confirms the transfer, the member whose turn it was answers "I received it" or "It has not arrived"; a "not arrived" answer appears in the console as a dispute for the officer. Novi still never holds the money (D2): the officer acts in the MFI's own console. A transfer that was released and then refused is still retried automatically (D49), and a held pot (D48) becomes ready as soon as it is full. Trade-off: a pot can leave later than its due date if no officer is at the console; reminders to the officer are a later step. The record (ACEV) can now distinguish pots confirmed by the member who received them.

### D64. Sandbox payments go through FedaPay's payment page, confirmed by its signed webhook (26 Oct 2026)
A probe of every "send now" variant (npm run fedapay:probe, 26 Oct) showed that this FedaPay sandbox account answers "Opération non autorisée" to /moov, /mtn and /mtn_open, and 404 to every other form, with both 8- and 10-digit Benin test numbers: sending a request straight to a phone is not enabled for the account. FedaPay's sandbox publishes test numbers for Benin only (MTN 66000001, Moov 64000001). Novi therefore uses FedaPay's hosted payment page in the sandbox: the API creates the transaction and its token, the app opens the page, she pays there with a test number, and FedaPay notifies Novi through the signed webhook; Novi then reads the true status back from FedaPay before crediting anything (D45). The flow is the same in live mode with Togolese operators, once FedaPay enables the account. Tested end to end on 27 Oct: the page succeeds with "Momo Test" and the number in Benin's 10-digit format, 0166000001 (Benin moved to 10 digits in 2024); the 8-digit 66000001 from FedaPay's documentation fails. Until then the pilot can stay on the mock provider, and the FedaPay flow is shown with a test number.

### D65. The ACEV is a signed one-page document with a fingerprint of the ledger (27 Oct 2026)
The shared record was a list of numbers on a plain page. A loan officer needs something she can file: the ACEV is now an A4 attestation with a number (ACEV- plus the share code), the holder's ID-checked name, the MFI that held the funds, four headline facts (share of payments on time, amount saved, pots received and how many their receiver confirmed, completed cycles), the groups, the method in plain words, and a verification block: the QR code, the Ed25519 signature's public key, and a SHA-256 fingerprint of her ledger lines up to the issue date. The fingerprint is inside the signed record, so it ties the attestation to the exact ledger it summarises; the database refuses any change to a ledger line (D46). The lender who scans the QR code and the MFI officer in the console see the same document, which prints or saves as PDF from the browser. Still facts only, no score (D33). Records shared before this date simply lack the new facts.

### D66. The MFI validates each group before its account opens (27 Oct 2026)
Until now, when the organiser pressed "Start", Novi asked the MFI to open the group's account at once. The MFI holds the money and carries the customer due diligence under BCEAO Instruction n°003-03-2025, so it should decide. With MFI_GROUP_APPROVAL set (on Render), a started group waits in STARTING and appears in the console under "Groups to validate", with its contribution, rhythm and size; the officer validates it, and only then is the account opened and the first round scheduled, or declines it with a reason, and the group is cancelled before any money has moved. Both actions are logged with the officer's name. What exactly an officer must check before validating (and whether she needs the members' names, which D33 withholds today) is a question for the MFI interview.

### D67. The console shows the MFI's portfolio over time and what its officers did (27 Oct 2026)
An analytics page gives, over eight weeks, the money collected and paid out per week, the share of payments made on time, the number of members, the groups by state, the pots paid out and how many their receiver confirmed or disputed (D63), and the median time a due pot waited for the officer's release. All figures are totals: no member's name (D33). A log lists every action by the MFI's officers, newest first: groups validated or declined, pots released, transfers retried, and ACEVs opened, with who and when. This is the trail an auditor or the BCEAO's supervisors would ask for, and it lets a branch manager see that pots are released on time.

### D68. A solidarity reserve, pooled across the MFI's groups, pays a late member's share (27 Oct 2026; replaced by D103 and D104 on 6 Nov)
When a member had not paid by the due date, her group's pot was held (D48) and the member whose turn it was waited, often for a temporary difficulty of a few weeks, which is how most late payments happen. Now 2% of every contribution is set aside (100 FCFA of 5 000; the member still pays 5 000, and a pot of three is 3 x 4 900). The shares of all the groups at one MFI form one solidarity fund held at the MFI: a single group's reserve, a few hundred francs, could never cover a whole share, while the pooled fund can from the first round. On the due date, if the fund holds enough, it pays every missing share, the pot becomes ready to release complete and on time, and each covered member owes her share; her late payment refills the fund. At the end of the cycle, what the group put in, less what its own members still owe, goes back through the MFI to the members who owe nothing, in proportion to what each put in. Each movement is a ledger line (RESERVE_IN, RESERVE_COVER, RESERVE_REPAY, RESERVE_RETURN). A covered round still counts as missed on her ACEV, which also shows how many covers she repaid: the fund protects the group, not the record. The idea of pooling the cover of temporary defaults across many borrowers was put forward by Abdou Sissé on "Déchiffrer l'éco"; whether a fund of this kind needs a specific BCEAO authorisation, and who carries a loss larger than the fund, are questions for the MFI interview.

### D69. Protecting the group: next of kin, death, departure, a lost phone and debt (27 Oct 2026)
A tontine has to survive what happens to its members. In all these cases the money stays in the group's account at the MFI (D2); what changes is who receives it and who may log in, always by the MFI officer at the counter, and every action is logged with the officer's name.
- Next of kin. In Me, a member names the person who receives what she is owed if she dies: name, relation and a Togolese number that is not her own. Home reminds her until she has done it, from her first group or invitation. Novi never contacts this person while she is alive, and her groups do not see who it is.
- Finding a member. The console's Members page finds a member of this MFI's groups by her phone number, with her legal name, next of kin, what she owes the fund, and her seats. It is the one place the console shows a name (an exception to D33), because the officer acts for a person standing in front of her, or on a death certificate; each lookup is logged. A number outside this MFI's groups is answered as unknown.
- Death. On the death certificate, the officer records it. Her account is closed and logged out everywhere. What the fund paid for her is written off, and the fund pays her remaining shares, so nobody else carries them and the others' reserve returns are not reduced: the loss is the pooled fund's (D68), the same logic as the death cover MFIs attach to loans. Her pot, at her turn, and her part of the reserve go to her next of kin's number, or to the heir's number the officer types from the documents. If she was the organiser, the role passes to the next member in the turn order.
- Departure. A member who stops taking part in a started group is recorded as having left. She still owes what the fund pays for her. Before any member's pot is released, what she owes the fund in that group is taken from it first, so nobody can collect the pot and leave her debt behind. If her turn has already passed, the debt stays.
- Debt. While a member owes the fund anything not repaid or written off, she cannot create or join another group (DEBT_OUTSTANDING). One ID-checked account per NIU (D12) means she cannot start again under a new name; recovering a debt after the cycle is the MFI's, as for any of its customers.
- A lost or stolen phone. She comes to the agency with her ID card; the officer records the new number. Every session is closed and every phone she had trusted must pass the SMS code again, now sent to the new number, so whoever holds the old phone is out. Her pots not yet sent follow the new number.
- A new organiser. The officer can name another member organiser, at the organiser's request or after the automatic handover.
Questions for the MFI interview: which documents it requires to pay an heir, and whether a death cover of this kind is allowed from the solidarity fund or needs an insurer.

### D70. Each group has its own chat (27 Oct 2026)
A tontine is a group of people who know each other, and its strength is the social pressure and support between them: today that happens in a WhatsApp group alongside the notebook. Each group now has a chat inside Novi, opened from the group's page, with the number of new messages on the group's page and on home. A member can write once she holds a seat (she accepted, or asked for a change to the rules, so the rules can be discussed there); an invited number that has not answered has no access, so the group does not learn who uses Novi (D38). Novi adds its own lines when money moves ("Abla paid round 2", "Round 1 pot paid to Akossiwa"), written in each reader's language, so the chat is also the group's running story and the reminder comes from peers, not only from Novi. Each line can be listened to. Messages are at most 500 characters, 10 a minute per member; a message is never edited, and its author or the organiser can hide it, leaving a "message hidden" line so nothing disappears silently (each hiding is logged). A member who left the group (D69) can read but not write. The chat is the group's only: the MFI and the console never see it (D33). A fixed warning at the top says that neither Novi nor the MFI will ever ask for a PIN or an SMS code, the scam most likely in a chat about money. The app asks for new lines every five seconds while the chat is open, rather than holding a live connection: nothing more to run on Render, and it copes with a weak mobile connection. Considered: linking to the group's WhatsApp (rejected: Novi could not add its payment lines, and members' phone numbers would be exposed to the whole group, while in Novi members see only names (D43)).

### D71. Groups hold scheduled voice or video meetings, on Daily (27 Oct 2026)
Some things a group settles better by talking: a late payment, the date of the next round, changing the rules. The organiser plans a meeting from the group's page from the moment the group is proposed until the cycle ends: a title, an optional agenda, a day and an hour chosen by touch (no date to type), and a length of 15 to 60 minutes. Novi asks the video provider for a private room the size of the group, which opens 10 minutes before and closes at the end, ejecting anyone still in it, and posts the meeting in the chat (D70). Each member who joins gets a personal pass, valid only for that room until the meeting ends, with her display name; the address alone lets nobody in. The organiser joins as the room's owner, so she can mute or remove someone. Members join with the microphone on and the camera off, to save data on a weak connection. The group sees who joined; nothing is recorded, and the MFI does not see meetings (D33). A member who left the group (D69) cannot join. Limits keep the provider's free allowance safe: at most 5 meetings planned ahead per group, never overlapping, at most 60 days ahead. If the provider does not answer, no meeting is created. The provider is Daily, behind an interface (D3) with a mock for tests. The call opens in the phone's browser, which works in Expo Go and in the APK without native code; Daily's React Native SDK would need a development build. Daily's plan includes 10 000 participant-minutes a month (a 30-minute meeting of five uses 150), then charges $0.004 a minute; the account needs a card on file. Considered: meet.jit.si (rejected: since 24 August 2023 whoever creates a room must sign in with a Google, GitHub or Facebook account); LiveKit Cloud (no card needed, 5 000 minutes; a good fallback, and open source, so an MFI could host it itself); Agora (needs a native SDK); 8x8 JaaS (25 users free, then $99 a month).

### D72. The organiser starts the next cycle with the same members in one step (27 Oct 2026)
A tontine rarely stops after one cycle: when every member has received her pot, the same women usually go again. On a completed group, the organiser taps "Relancer un cycle". Novi creates a new group with the same name and rules, numbered (cycle 2, 3, …) and linked to the cycle before, and invites again every member who completed the cycle. It is a draft, so she can change the amount or the size first, then propose it; each member accepts the new cycle herself, since consent is given per cycle (D29), and the MFI validates it like any group (D66). Members who left or died (D69) are not invited again; a member who still owes the solidarity fund is invited but cannot accept until she has repaid (D69). Each cycle stays its own group, so its ledger, pots and reserve return are closed and the ACEV counts it as one completed cycle. Only one next cycle can be started from a group.

### D73. Novi by USSD, through Africa's Talking's gateway (27 Oct 2026)
Many traders at Assigamé have a basic phone, or a smartphone without data at the end of the month. USSD works on every GSM phone, without internet, and is what they already use for mobile money. Novi now has USSD menus: the member dials a short code, enters her PIN (checked with the same lockout as the app, D18), then 1 pays this week's contribution (choosing Moov Africa or Yas, then approving the request with her mobile money code), 2 sees her groups (round, paid or not, her turn), 3 sees her record (ACEV), 0 quits. Each screen stays under 160 characters. A USSD payment lands in the same group, ledger, chat and ACEV as one made in the app: two doors to one system.
The menus are reached through Africa's Talking's USSD gateway: at each key press it posts the session, the member's number (which the operator vouches for) and everything typed so far, and shows Novi's plain-text answer ("CON" to continue, "END" to close). The gateway does not sign its requests, so Novi's address for it contains a secret (USSD_CALLBACK_TOKEN); without it the address does not exist. Until a real code exists, the channel is Africa's Talking's free sandbox: their servers call Novi on Render exactly as for a live code, and only the handset is their browser simulator. In pilot mode only the 20 test accounts may use it, since a real member's PIN is typed only on her own phone.
A live code in Togo needs an agreement with each operator (Moov Africa and Yas): Africa's Talking does not list Togo among its USSD countries, and operators contract with a registered company. ARCEP's decision n° 038/ARCEP/DG/20 of 23 November 2020 caps, from 1 January 2021, what an operator may charge a service provider: 250 000 FCFA excluding tax to set up a code, 150 000 FCFA a year for maintenance, and 3 FCFA excluding tax per session (down from 100 FCFA). For 500 members using it four times a month, that is 2 000 sessions, about 6 000 FCFA a month in all, plus the fixed fees. Considered: a simulator inside the MFI console (rejected: USSD is the member's channel, and an officer should never type a member's PIN). Revised 29 Oct: in the sandbox, any pilot account may use the code, not only the first 20 test numbers, since every pilot account was opened with a demo identity (the simulated ANID accepts nothing else); once the real ANID is connected, the sandbox is closed to all accounts.

### D74. Ewe texts are written by a native speaker, from a sheet of key sentences (27 Oct 2026)
Many members speak Ewe first. Machine or AI Ewe is not reliable enough for words about money, so Novi's Ewe comes from a native speaker. docs/ewe/key-sentences.csv lists the 57 sentences of the core journey (language choice, home, paying, the group, the pot, the chat's safety warning, meetings, next of kin, the next cycle), each with its French and English. Once the "eʋegbe" column is filled, `node scripts/importEwe.mjs` (in apps/mobile) copies the sentences into the app, refusing any sentence that lost a word the app fills in, such as {{name}} or {{amount}}. Any sentence not yet translated falls back to French. The Listen button still reads Ewe with a French voice, as phones have no Ewe voice; recorded audio by a native speaker remains the plan.

### D75. A splash screen, and sign-up and login in the wax look (27 Oct 2026)
The first screens a member and a jury see were the plainest of the app. Novi now opens on the orange of its app icon, so tapping the icon flows into the splash, with its mark, three cowries fanned out (gold, ivory, teal; the orange shell turns gold, the colour of the coins in the pot) above the word "Novi" in white: first the phone's own splash (expo-splash-screen, the same picture as a still image), then the cowries spring in and a line appears, "Épargner ensemble, en confiance", before the app fades in, about a second and a half, once per launch. The way in follows a design reviewed on a canvas of mock screens before it was built: a welcome screen that continues the splash's orange, with Novi's mark and name, the three languages as one-tap buttons at the top, and two clear ways in, "Créer mon compte" and "J'ai déjà un compte", as in most apps. Every sign-up, login and forgotten-PIN screen is a plain cotton screen, everything aligned to the left: back and Listen, then for a sign-up step its name and a progress bar ("Étape 1 · Votre numéro"), then the title and one line. Logging in on a new phone is a classic form: the number, the PIN in four boxes (a dot per digit, never the digit), "PIN oublié ?" just under it, and the button. On her own phone, her account is shown in a card ("Compte sur ce téléphone", her initial and her number partly hidden, with "Changer"), so she understands why the number is already there. A first version used cowries for the PIN; it was dropped as confusing: cowries are Novi's decoration, never a control. The rules behind the PIN do not change (D16, D18).

### D76. Calling the group and voice notes in the chat (28 Oct 2026)
Members of a tontine talk more than they type, and many read little. The Discussion tab now has "Appeler le groupe": any active member calls the whole group at once, as she would ring her neighbours. Novi opens a private Daily room (the provider of D71) for 30 minutes, posts "Akossiwa a lancé un appel · Rejoindre" in the chat, and gives each member her own pass; if a call or a planned meeting is already open, she joins it instead of opening a second room. Calls are not planned meetings: they do not appear in the meetings list or count towards its limit of five. The chat also takes voice notes: hold the microphone, speak, let go to send, slide left to cancel, one minute at most. The phone records small (mono AAC, about 32 kbit/s, so a full minute is about 240 KB), the server refuses anything longer or larger, and the sound is stored apart from the message. A voice is more personal than a written line, so a hidden voice note loses its sound at once, and every voice note of a group is deleted when its cycle ends; the written chat stays. The MFI hears none of it (D33). Free tier: Daily gives 10 000 participant-minutes a month; a 30-minute call with 15 members uses 450.

### D77. A running group lives in three tabs, with less explanation on screen (28 Oct 2026)
The group page had grown into one long page: the round, payments, the reserve, the chat, meetings, rules and turns, one under the other. Following a design reviewed on the canvas, a running group now has three tabs: "Cotisation" (what she owes this round and the Payer button, who has paid, who receives on the due day, when her own turn comes), "Discussion" (the next meeting and the calendar, Appeler le groupe, the chat) and "Le groupe" (who receives on which date, readable with fifteen members: the pots already received in one line, the current turn, the next four, her own turn, then "Voir les 15"; the caisse de secours; the rules; the register). The "réserve solidaire" is now called the "caisse de secours", the words the members would use, and its explanation is behind a "?". The meetings screen shows a month calendar, meetings in navy, payment days with an orange dot. Across the app, the long explanations were cut to a line: screens show amounts, dates, names and buttons, and the explanations are in Listen and behind "?". Warnings that protect money (never share a PIN, check the number before inviting) stay.

### D78. Ewe: Claude drafts, a speaker checks, a free machine voice reads only what a person kept (28 Oct 2026)
Refines D74. The sheet now has 64 key sentences and a column "brouillon_claude": a first Ewe draft by Claude, to be corrected, never shipped as is; only the "eʋegbe" column, written or checked by a speaker, reaches the app. For the Listen button, Novi uses Meta's MMS text-to-speech model for Ewe (facebook/mms-tts-ewe), free and run once on a laptop (scripts/ewe_voice.py): it reads each checked sentence into a clip. Nothing reaches the app until a person has listened to it in the voice studio (npm run voice:studio, a page on the laptop): for each sentence she can correct the text, keep the machine voice ("Ça sonne juste") or record her own voice. Kept clips are bundled in the app and reach phones with an update, so Listen works in Ewe without internet. Sentences with a name or an amount are not voiced, as the voice cannot know them in advance; the screen shows them, and the phone's French voice reads what has no clip. The MMS licence is non-commercial (CC BY-NC 4.0): fine for the capstone and the demo; for a pilot, the clips are replaced by recordings of a speaker through the same studio. Considered: GhanaNLP's Khaya API (rejected for now: no published free tier) and an Ewe voice cloned from a sample (F5-TTS, rejected: too heavy to run for a student project). The models learned Ewe largely from Bible readings recorded in Ghana, so the accent may not sound like Lomé's market: a speaker's ear decides.

### D79. Phone notifications for calls, chat and money (28 Oct 2026)
Without notifications a member learns of a call, a message or her pot only by opening Novi, which made "Appeler le groupe" (D76) of little use. Novi now sends phone notifications through Expo's push service, which is free and forwards to Google's (FCM) and Apple's services, at four moments: a member calls the group ("Abla appelle Pagnes Assigamé", to everyone else), new chat messages (at most one notification an hour per member and group, and none while she has the chat open, so the phone does not buzz all day at the market), her pot is paid, and a payment is due tomorrow or today (alongside the SMS of F16, which still reaches basic phones). Tapping one opens the screen it is about. On Android they come in three channels the member can tune in her phone's settings: money and calls ring, chat is quieter. In "Mon compte" she can switch off chat notifications; money ones cannot be switched off, as they protect her money. A phone gets notifications only while she is logged in on it: logging out, a new number or a closed account (D69) stop them. The texts carry no amounts other than her own, and nothing about other members' payments. Android needs a Firebase project (its google-services.json in the app, and its FCM key uploaded to EAS, never committed); the app's version moves to 0.2.0, so the over-the-air updates for it never reach the older APK, which lacks the module.

### D80. "On continue ?": each member says whether she goes again (28 Oct 2026)
Refines D72. When the last pot is paid, each member who completed the cycle answers in one tap, "Oui, je continue" or "Non, j'arrête", and can change her answer until the next cycle is started. The whole group sees the answers by name, as at the market, and a notification asks the question. When the organiser starts the next cycle, everyone is invited again except those who said they stop; a member who has not answered is invited, and can still decline. So nobody is pressed into a new cycle by a group invitation, and nobody is left out by a missed tap.

### D81. The MFI's administrators manage their team in the console (29 Oct 2026)
Refines D52. Officers release members' money, so the console has no sign-up page; until now an account could only be opened by running a command on the server, an officer could not change the password it printed, and nobody could close the access of an officer who left the agency. Now the command is used once per MFI, for its first administrator (for example the branch manager). After that, administrators manage the team on the console's "Équipe" page: they add an officer (name, email, role: officer or administrator), and the console shows, once, a temporary password and a QR code for the authenticator app, to be handed over in person, never by SMS or WhatsApp. At the first login the officer must choose her own password (at least 12 characters); until then the console stays closed. An administrator can deactivate an officer, who is logged out at once and cannot log in (her past actions stay in the Journal), reactivate her, or reset a lost access (new temporary password and new authenticator key, so the old phone's codes stop working). An administrator cannot deactivate herself or the last administrator, and never reaches another MFI's officers. Every addition, deactivation, reactivation and reset is written to the Journal with the administrator's name. Considered: Firebase Authentication for the console (rejected: the console already has two-factor login, which Firebase offers only in its paid Identity Platform, and each officer's MFI and role would still live in Novi's database, so two lists of officers would have to be kept in step).

### D82. In the pilot, an officer can bring a due date forward, for tests and demonstrations (29 Oct 2026)
A round falls due on the first due day after the group starts, never the same day (D44), so a tester or a jury could not see a pot released on the day the group was made. In pilot mode only, the console's group page has a dashed button, "Avancer l'échéance à aujourd'hui (démo)": the group's next unpaid round becomes due today, and the payout job runs for that group at once, so a full pot appears "À libérer" for the officer to release as usual. Rounds before it that were also due today move to yesterday, so the brought-forward round is the one open for payment and a whole cycle, up to "On continue ?", can be shown in one session. It never sends money by itself, only moves the date; it works only on the officer's own MFI's running groups, and each use is written to the Journal. Outside pilot mode the button is not shown and the address does not exist.

### D83. After a pot is paid, the group page moves on to the next round, which can be paid ahead (29 Oct 2026)
Rounds follow the calendar set at the start: nobody, not the organiser and not the MFI, can move a turn forward or skip it (D44), and the next round opens by itself the day after the previous due date. Between a release and that day, though, the Cotisation tab still showed the finished round, with nothing about what comes next. Now, as soon as the current round's pot has been paid out, the tab shows one line, "Tour 1 terminé · versé à Afiavi", and below it the next round: its date, who receives it, and who has paid. A member who has paid the current round may pay the next one ahead ("Payer en avance"), as a trader with money today often prefers to set it aside; she can never pay further ahead than the next round, so nobody pays a whole cycle in advance. An early payment waits in the group's account like any other until that round's due date, when the pot is released as usual.

### D84. FUCEC validates a group by seeing each member's Novi record, with her consent given when joining (30 Oct 2026)
Revises D33 and D37 for group validation (D66). An officer asked to validate a group used to see only totals, so the validation step meant little: he could not tell who he was opening an account for. Now each member, when she accepts the rules (and the organiser when she sends them), ticks "J'accepte que FUCEC voie mon historique Novi"; joining needs this tick. On the group's page the officer then sees, for each member who agreed: her name as on her ID, the date her identity was verified, how many tontines she completed on Novi, how many payments she made and how many were on time (paid by the end of the due day), and what she still owes the emergency fund. He never sees her messages, her voice notes, or which round she paid late. A member who joined from an older app without the tick appears as "N'a pas accepté de partager son historique"; the officer can still decide. Reason: the supervisor asked why the MFI validates a group it cannot see; an MFI identifies its customers anyway, and consent recorded per group keeps the member in control (D37). The same record will back loan requests (next decision).

### D85. Group calls open inside Novi (30 Oct 2026)
Revises D76. A call or a meeting used to open in the phone's browser, so the member left Novi and had to find her way back. Now it opens in a full-screen page inside Novi (a web view showing the Daily room), with the group's name and a "Quitter l'appel" button on top; only Daily's own addresses may load there. Android asks for the microphone first. This needs the web view built into the app, so it works on the next APK (and in Expo Go); a phone still on the older Novi falls back to the browser, as before, so nobody is blocked. The FedaPay test page will move inside Novi the same way.

### D86. The payment page opens inside Novi (30 Oct 2026)
Follows D85. In the pilot, FedaPay's sandbox cannot send a request to a test phone, so a member approves her payment on FedaPay's checkout page (D64), which used to open in the browser. It now opens in a page inside Novi, titled "Payer 5 000 F" with "Page sécurisée FedaPay" and a "Fermer" button; only FedaPay's own pages load there, and any other link opens in the browser. Novi keeps checking the payment and closes the page by itself once it is confirmed, back on the round with the receipt. With live mobile money there is no page at all: Moov Money or Mixx by Yas shows the request on her phone and she types her own code, which Novi never sees. Like the call, this needs the web view in the app (next APK, or Expo Go); an older Novi still opens the browser.

### D87. Members can swap turns, with the partner's yes and the organiser's confirmation (1 Nov 2026)
Traders already swap turns by hand when one needs money sooner: Abla's daughter needs school fees in two weeks, Dzifa can wait. In Novi, a member picks another member whose turn has not come yet; that member accepts or refuses; then the organiser confirms (her own yes is enough when she is one of the two). Only turns not yet paid out, and not due today or earlier, can move, and each member has at most one swap open per group. On confirmation the two seats exchange their payout positions and the two rounds their receivers, in one transaction; the group's chat shows "Abla passe au tour 4" and "Dzifa passe au tour 2". No money is lent, so there is no interest and no credit question: only who receives which pot changes. Considered: letting the organiser reorder freely (rejected: the order is drawn or agreed once so nobody can arrange it to suit herself, D44).

### D88. A small advance from the solidarity fund, repaid from her own pot (1 Nov 2026)
For an emergency (an illness, stock lost in a market fire), a member may ask the solidarity fund (D68) for an advance of 500 F up to one contribution. Conditions: the group is running; she has paid every round already due and owes the fund nothing; her own pot is still to come (it is the guarantee); one advance at a time. The organiser and one other member approve (two other members when the organiser is asking); one refusal ends it. The MFI officer then sends it from the console, like a pot, through the MFI. When her turn comes, her pot repays it first, before anything is sent to her, with no interest; every movement is a ledger line (RESERVE_ADVANCE out, RESERVE_ADVANCE_REPAY back). The fund is shared by all the groups at the MFI, so the advance is also capped by what the fund holds; in a small pilot it may hold too little, and the app says so. Why no interest: savings groups often charge 5 to 10 % a month, but the UMOA usury ceiling for microfinance is 24 % a year (BCEAO; maintained for 2026), and the money is held by a licensed MFI. A VSLA-style loan fund (members save extra, borrow up to 3 times their savings for up to 3 months, interest capped at 2 % a month) is the next step, and needs the MFI's agreement.

### D89. Microloan requests to the MFI, carried by Novi with the member's record (1 Nov 2026)
Revises D37: the request itself is the member's consent that the MFI sees her Novi record for it. She may ask when her record shows she pays: a tontine completed on Novi, or 8 payments on time in a row; 90 % or more of her payments on time (paid by the end of the due day); nothing owed to the solidarity fund; no other request open; 30 days since a refusal. She chooses the amount (suggested ceiling: 3 times her largest pot), what it is for (stock, equipment, other) and the length (3, 6 or 12 months). The officer sees the request with her name, ID check, groups, payments and on-time rate, and grants the same amount or less, or declines with a reason she reads. A yes says "venez à votre agence avec votre carte d'identité": the MFI decides, lends at its own rate (within the 24 % usury ceiling) and is repaid at its agency. Novi neither lends nor moves this money. Reason: the supervisor asked for a path from saving to credit; the record Novi builds is exactly what a loan officer lacks for women with no payslip.

### D90. Officers are told by email, outside the console, and late items go to the administrator (1 Nov 2026)
So a member is never kept waiting because nobody looked at the console. Every active officer and administrator of the MFI gets an email, with a link straight to the page, when: a group waits for validation (D66), a pot is ready to release (D63), a member says her pot did not arrive, a loan request arrives (D89), or an advance is approved (D88). Each working day at 08:00 (Lomé is on GMT), one summary of everything still waiting, if anything is. Anything still waiting after 4 working hours (Monday to Friday, 08:00 to 17:00) is emailed again to the administrators, once. Members are never emailed; they have phone notifications (D79). Provider: Brevo's transactional email API (free plan, 300 emails a day), behind an interface with a mock, like every other provider (D3). The human click to release money stays: automatic release is a scaling option, not a default.

### D91. The MFI sets its own credit conditions; a request is preselected, documents are checked, the decision is taken at the agency (1 Nov 2026)
Revises D89. The conditions for asking for a microloan are no longer fixed by Novi: the MFI's administrator sets them in the console ("Conditions de crédit": whether requests are open, finished tontines or an on-time streak, the minimum share of payments on time, the ceiling as a multiple of her largest pot, the wait after a refusal, the lengths offered, and the documents required), with a preview of how many members would qualify; every change is written to the Journal. Novi applies the conditions and shows the evidence, condition by condition with her own figures, both to her ("Vous : 87 % (13 sur 15). Encore 5 paiements à l'heure.") and to the officer. The officer's first answer is no longer a loan: "Présélectionner" means her record convinces the MFI, which asks for her documents; or he declines with a reason. Once preselected she agrees to send photos of her documents through Novi; the officer opens each one (each view logged) and accepts it or asks for a new photo; when all are accepted she is told to come to the agency with the originals, where the MFI decides. The officer then records the outcome (granted, with the amount, or not). Photos are seen only by that MFI's staff and deleted 30 days after the file is complete or closed (60 days if it is left unfinished), under Togo's data protection law (Loi n° 2019-014). Reason: a lender owns its credit policy, and nobody should read "accordé" before the lender has actually decided; photos save a trader a wasted trip from her market to the agency, but the MFI still sees the originals and identifies her in person, as anti-money-laundering rules require. Paying out and collecting the loan through Novi is out of scope (D34) and on the roadmap with the MFI's agreement.

### D92. Home like a bank app, the ring of members, daily groups (1 Nov 2026)
Testers found the member app confusing: Entraide and Crédit were hidden in a tab or in Mon compte, and nothing on home said which group an action applied to. The member app now follows the structure of the bank and mobile money apps traders already use (direction "Lagune", canvas boards E1 to E7): a blue band with her name and Novi's own pagne motif; one card per running group, swiped like accounts, showing the round as a ring of members in turn order (green when paid, her seat in orange, a saffron dot on whoever receives), what she owes and by when, who receives the pot, and a Payer button with a cowrie, West Africa's old money; the group's own actions sit on its card (Appeler, Discussion, and Plus for swapping a turn, an advance, meetings, the rounds and the members), so an action can never be applied to the wrong group; "Pour vous" holds only what concerns her and not one group (credit from the MFI, a new group, sharing her record); "Dernières nouvelles" lists what moved in all her groups, like a bank statement. The bottom bar is the same everywhere: Accueil, Groupes, a raised orange Payer (straight to the round she owes, or "Pour quel groupe ?" when she owes in several, or "Rien à payer"), Historique (her record, now with every payment marked on time or late) and Compte. The API adds the receiver's name and each seat's payment to the home summary, GET /v1/me/news (money and meeting lines of her groups' chats over 30 days, only groups she joined) and GET /v1/me/statement (her payments and pots, line by line, for her eyes only). Groups can now pay daily, Monday to Saturday, as market tontines in Lomé often do: a daily group has no day to choose, its rounds skip Sundays, and it gets one SMS reminder on the morning of each payment day instead of two. Pots of daily groups are still released by the MFI officer (D63). A group's page follows the same look (board E5): the blue band with who organises and which MFI holds the money, a phone to call the group, the three tabs as one control, this round's members as faces in turn order, and the group's actions as tiles; the payment screen reads like a mobile money confirmation (what she pays, for which round, who receives, her service as two big choices). The MFI console takes the same identity (boards K1 to K4): a night-blue sidebar with the number of things waiting, white cards, and orange only for the action that moves money; the overview becomes one "À traiter" list, most urgent first, each line with its own button (pots to release, disputes, failed transfers, advances to send, groups to validate, loan requests, held pots); a group shows this round as an anonymous ring of how many paid, never who (D33), its money and its rounds as a strip; the Journal names the group or member, the round and the amount in the officer's language, includes every credit step and advance, and can be filtered and searched. A disputed pot now dates from the member's "not received", not from when it left. The rest of the member app follows: soft blue lines instead of navy outlines, sky-blue back and Listen buttons, chips and progress in lagoon blue (orange stays for paying), no labels in capitals, the discussion's own messages in lagoon blue, and a flat sky band on the secondary screens. The payment screen used to show the pot divided by the members (4 900 FCFA for a 5 000 FCFA contribution, since 2% goes to the caisse); it now shows what she actually pays. Reason: familiar on the outside, so nothing has to be learned; Novi's own on the inside (the ring, the pagne, the cowrie), so it is not mistaken for a template.

### D93. The pilot can start again from zero groups (1 Nov 2026)
Weeks of tests left the pilot console full of groups that no longer mean anything (disputes on sandbox money, held pots of abandoned groups), which would confuse the defence and the tests with traders. `npm run demo:reset`, run only from the server's shell, first shows what it would erase; with `-- --yes` it erases every group and everything that happened inside one (rules, invitations, rounds, payments, pots, ledger lines, the caisse, chats and voice notes, meetings, swaps, advances), every loan request with its documents, every shared record, the staff alerts and the Journal's lines about them. Members keep their account, verified identity and PIN; officers keep their logins; the MFI keeps its credit conditions. The ledger is append-only (D5) and its trigger refuses any deleted row; TRUNCATE does not fire row triggers, so the reset empties it on purpose, once, for test data. It refuses to run unless the server is in pilot mode (PILOT_SHOW_CODES=true), so it can never touch a real deployment's money records.

### D94. Five planned features are deferred, and what took their place (1 Nov 2026)
The build brief (13 Oct) planned features F1 to F19. Five were not built, by choice, and the time went to what the supervisor's reviews (16 and 29 Oct) and the tests on phones asked for. Each one is recorded here with what replaced it, so the scope can be read as decided, not as left unfinished.
- F12, the carnet (daily sales and expenses). It was meant as proof of trade for a lender. A trader's own notes are self-declared, so a lender gives them little weight, and keeping them daily is work traders do not ask for. Replaced by two stronger proofs: her payment history, taken from the ledger and signed (D50, D65), which the MFI reads with her consent (D84, D89); and a document photo of her activity (a trader card, a market ticket or a supplier's invoice) in the credit file (D91). Roadmap: a light carnet if a partner MFI asks for cash-flow figures.
- F13, three-way reconciliation (Novi's ledger, the MFI's books, mobile money). It needs read access to the MFI's account statements, which no partner MFI exposes through an API, and FedaPay's sandbox cannot settle real transfers (D64). What exists: every payment and pot is credited once, only on the provider's signed confirmation (D45), the ledger is append-only in the database (D46) and fingerprinted (D65), and the console shows, per group, collected, paid out and the balance the MFI should hold, so an officer can compare it with his own system. Roadmap: automatic matching once an MFI provides a statement export.
- F15, offline copies of the ledger and carnet (WatermelonDB). Without the carnet, what remained offline was reading the ledger, at the cost of a sync layer and conflicts on money data. A trader with no data reaches Novi by USSD instead (D73), on any phone and without internet, to pay, see her groups and her turn. Roadmap: a read-only offline view of her groups.
- F19, an assistant answering questions about her own group. A wrong answer about money (what she owes, when her turn is) does real harm, and a model cannot be checked in Ewe (D74). Its job, finding the answer without reading much, is done by the screens themselves: home answers "have I paid, who receives, when is my turn" at a glance (D92), the Listen button reads every screen aloud (D78), and the group can call or meet in Novi (D71, D76, D85). The advanced feature chosen among F17 to F19 is F17, group meetings, built with live voice and video rather than saved audio: recording people needs everyone's consent each time, and no member asked to replay a meeting.
- The map of the nearest FUCEC agencies (chosen on 25 Oct). FUCEC's list of agencies with locations was not available to check, and a wrong address sends a trader across Lomé for nothing. The credit flow tells her when to go to her agency and with which originals (D91). Roadmap: the map, once FUCEC confirms its agency list.
F18 (find a group in your market) was dropped earlier for safety (D40). In their place the build added, at the supervisor's request or from testing: MFI validation with each member's consent (D66, D84), the release of each pot by an officer and the member's receipt (D63), the solidarity fund and its advances (D68, D88), turn swaps (D87), loan requests under the MFI's own conditions with documents (D89, D91), calls and payment inside the app (D85, D86), officer emails (D90), the chat and notifications (D70, D79), the next cycle (D72, D80), protection on death or departure (D69), daily groups and the bank-style home (D92).

### D95. The group chooses where its money is kept, as part of its rules (6 Nov 2026)
Until now every group was attached to FUCEC-Togo by the code, although D36 says Novi works with several MFIs and never exclusively (Instruction 001-01-2024, Art. 7). The MFI is now part of each version of a group's rules (`rules_versions.mfiId`): the organiser chooses it among the partner MFIs when she creates the group ("Où l'argent est gardé"), every member sees it in the invitation and accepts it with the amount and the rhythm (D29), and a member who prefers another one asks for a change. Changing it creates a new version, so every member answers again, and any agreement to share a record given to the previous MFI is erased (D98). Once the group has started its account is open at that MFI, so the choice can no longer change; the next cycle stays at the same MFI unless the organiser changes it before proposing. There is one console for every MFI: each officer's account belongs to one MFI and sees only its groups, money, loans and journal (D52), so the group's validation, its pots and its solidarity fund (D68) go to the MFI it chose. Partner MFIs are added by `npm run mfi:create -- CODE "Name"` on the server; the pilot adds a clearly named test MFI ("MFI de démonstration") and never shows a real institution as a partner without an agreement. An app that sends no MFI (an older version) gets the default partner, so installed phones keep working.

### D98. Sharing her record with the MFI is optional, and only while it validates the group (6 Nov 2026)
Revises D84. Someone familiar with traders warned that an MFI seeing their financial history could hold back adoption, and the D84 tick could not be refused without refusing the group. The tick is now optional for members and the organiser alike: she can join a group without it. Its text names what is shared (all her Novi tontines, her payments on time, what she owes the solidarity fund, never her messages) and says that the MFI stops seeing it once the group is checked. The console shows members' records only while the group waits for validation (STARTING); once the officer validates or declines it, the table is replaced by a sentence saying records are visible only during validation. Without her agreement the officer sees her turn and "has not agreed", nothing else. Her record still reaches an MFI when she asks for a loan (D89, D91), which is her own request. Whether traders accept this level of visibility is a question for the survey: comfort with the MFI seeing each payment versus totals only, and willingness to join if the MFI can see her history.

### D101. Officers' authenticator keys are kept encrypted (7 Nov 2026)
An MFI officer logs in with a password, which is stored only as a hash, and a code from his authenticator app (D52). The server must read the authenticator key back to check that code, so it cannot be hashed; until now it was stored as plain text, and a copy of the database alone would have let someone produce an officer's codes. The key is now encrypted with AES-256-GCM, which also detects any change to the stored value. The encryption key lives only in the server's settings (SECRET_BOX_KEY, or derived from JWT_SECRET when that is not set), never in the database. A key saved before this change is encrypted at its owner's next login. Changing the encryption key makes stored keys unreadable, and officers then need new ones (the team page's reset, D81).

### D103. An advance of half a contribution, paid with round 1, replaces the 2% reserve (6 Nov 2026)
Revises D68 and D88. The 2% reserve was too small for the risk that matters most: a member who receives her pot early and then stops paying. In a group of five at 1 000 F, she leaves a hole of 4 000 F, while 2% brings in 100 F a turn. Each member now pays an advance of half a contribution with round 1 (500 F on 1 000 F, rounded up to the franc), on top of the contribution: 1 500 F in round 1, then 1 000 F. It is her own money, not a fee: it stays at the MFI in the group's advances and comes back to her at the end of the cycle. Nothing is taken from later contributions, so every pot is the full contribution times the members. The advances are kept per group, not pooled across the MFI's groups, which removes the question of a BCEAO authorisation for a pooled fund. Round 1 is never covered: it carries the advances themselves, so its pot is held until everyone has paid it, and the group really starts only then. Advances for an emergency (D88) now come from the group's own advances. Considered: a whole contribution in advance (rejected: at 200 000 F a turn, 1 000 000 F before starting is out of reach); keeping the 2% as well (rejected: one mechanism is simpler, and the 2% was a real cost to traders).

### D104. One cover order for a missing share; "Je ne peux pas payer ce tour"; deadlines and default (6 Nov 2026)
Revises D68 and D69. Whatever the cause (no money that week, refusal, death), a missing share is covered in one order: her own advance, then her pot still to come, then the other members' advances in proportion; only when the advances are empty is the pot held (D48). In the books this is one pool per group: what she owes is taken from her pot first (D69), and at the end of the cycle a member who still owes gets no advance back, so her own advance pays first and only a larger loss is shared by the others, the way a paper tontine absorbs it, but smaller, fair and recorded. The member whose turn it is never needs the advances: her own share is taken from her pot.
The cause only changes her record. Before the due date she can say "Je ne peux pas payer ce tour": her share is covered at once and it is not a late payment if she repays in time. At most twice in a cycle, never two turns in a row, never while she still owes a cover, never for round 1 or her own turn. She repays by paying that round, within 7 days or by the next turn's day if that is later (a daily group would otherwise give her one day). The organiser can extend the deadline once, by the same length. A deadline that passes unpaid is a missed turn; a second one puts her in default: she stays in the group as a debtor, her pot (if still to come) repays first, and she cannot join or create a group until she repays (DEBT_OUTSTANDING). She is never deleted. After a death, nothing is held against her: if her pot is still to come it repays her shares and the rest goes to her next of kin; if she had already received it, the group's advances carry her shares. The other members are told, without a name, when their advances cover a share. A member with no Novi history (no completed cycle) never takes turn 1, the turn where receiving and leaving costs the group most: a drawn order gives it to the first member with a history, or else to the organiser, who vouches for those she invited; a fixed order that breaks this is refused (TURN_ONE_NEEDS_HISTORY). Questions for the MFI interview: who carries a loss larger than the group's advances, and whether 7 days matches what traders already tolerate.

### D105. The MFI works by exception: small pots leave alone, large ones need two officers (7 Nov 2026)
Revises D63 and D90. With one officer pressing "Libérer" for every pot, 1 000 weekly groups mean about 1 000 clicks a week, and a pot waits whenever nobody is at the console. Now each MFI has an automatic release limit, 50 000 F by default (a weekly group of 10 at 5 000 F), which its administrator changes or turns off in Équipe. A full pot up to the limit leaves on its due date with no officer; it is logged as released by Novi under the MFI's limit. A pot above the limit needs two different officers: the first approves (1/2), and only a second one can release it (2/2); the first cannot do both, as in a bank's four-eyes rule for large transfers. Raising the limit lets a waiting pot leave on the next run, unless an officer already approved it. Turned off, one officer releases every pot, as in D63. Nothing else changes: a pot that is not full is still held and never sent short (D48), a refused transfer is still retried (D49), and the member still confirms receipt.
"À traiter" now also lists the payments a member says left her account though the operator did not confirm them (D110). Here the officer sees her display name, the number that paid, the operator and the amount, because he must find the payment on the operator's statement; this is the one place the console names who paid (an exception to D33, for her own benefit). Found: the payment is credited exactly as if the operator had confirmed it. Not found: she is told by notification (and by SMS without the app, D111) to pay again, and the app lets her. While the MFI checks, she cannot pay that round a second time. The officers are emailed when a payment is reported, like every other item (D90).
Considered: a second limit for the two-officer rule (rejected for the pilot: one number is easier for an MFI to reason about); letting the officer mark a payment found without the operator's statement (rejected: the statement is the only proof the money moved).

### D109. Real SMS through Twilio, in GSM characters, under a monthly limit (7 Nov 2026)
Follows D61. With SMS_PROVIDER=twilio and its three keys (TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_FROM), the API sends real SMS; otherwise the mock still prints them to the log, and tests always use the mock (D3). Twilio was chosen over Plivo and Africa's Talking because one account reaches both Togo, where the members are (about 0.49 USD an SMS), and Rwanda, where the pilot is run from ([0.3261 USD](https://www.twilio.com/en-us/sms/pricing/rw)), and its trial account lets the author test with verified numbers before paying; Africa's Talking does not list Togo. Texts are turned into GSM characters before sending (« » become ", ê becomes e; é, è, à, ù stay), because one character outside that alphabet makes an SMS hold 70 characters instead of 160 and cost up to three times more. SMS_MONTHLY_LIMIT (200 if unset) caps a month: over it, an SMS is skipped and logged, never blocking a payment or a payout; each SMS really sent is one row in sms_logs. An SMS that fails is logged, never thrown, for the same reason. New money SMS: a payment the operator did not confirm, and a share the group's advances covered without her asking (D104), with what to repay and by when. A share she asked to have covered gets no SMS: she just saw it in the app.

### D110. "Mes transactions": her own money as a table, and "the money left my account" (7 Nov 2026)
Asked by the supervisor: a member sees her own transactions, not only her group's. The statement (D92) becomes a table: date, detail (what, which group, which turn), paid, received, and a total per month, filtered by direction and by group. Her advance has its own line (D103), and so does its return at the end; a share the advances covered shows with its deadline, or "remboursée" (D104); a payment pending or not confirmed shows too, struck through when it failed. A failed attempt disappears once she has paid that round. Tapping a payment to check or a share to repay opens its round. On a payment the operator did not confirm, the round asks one question, "Votre argent a-t-il quitté votre compte ?": yes flags it for the MFI to check against the operator's statement (it then appears in the officer's list, D105) and tells her not to pay a second time; no lets her pay again. Two buttons side by side (report, pay again) were rejected: she could easily pay twice.

### D111. SMS only when nothing else reaches her; Pindo for the pilot's Rwandan numbers (7 Nov 2026)
Revises D109. At Twilio's price, a member of a weekly group of 10 would cost about 31 SMS a cycle (10 receipts, 20 reminders, 1 pot), about 15 USD, as much as two of her contributions. So a member who uses the app (a trusted phone with a notification address, seen in the last 30 days) gets notifications, which are free, and SMS only for what must reach her even with no data: the sign-up code, her pot sent, a payment not confirmed, a share the advances covered. A member without the app (USSD) gets those too, and one reminder on the morning of the due date if she has not paid, but no receipt (her operator already texts her when the money leaves, and USSD shows it as paid) and no reminder the day before: about 2 to 4 SMS a cycle.
The pilot is run from Kigali. Rwandan numbers (+250, 9 digits) are accepted only when PILOT_RWANDA=true, on the pilot server, and the app then shows a +228 / +250 switch on the phone fields; the product stays Togolese. SMS are routed by the number's country: +250 to Pindo, a Kigali provider at about 0.01 USD an SMS on MTN Rwanda (Pindo's calculator, Nov 2026), set with PINDO_API_TOKEN and PINDO_SENDER; +228 to Twilio when configured, or simulated. Pindo does not reach Togo. For Togo, BulkGate quotes 0.0396 EUR on Moov and 0.261 EUR on Togo Cell, less with a sender name registered with the operators (about a month); a direct contract with Moov or Yas, or the MFI's own SMS contract, would be cheaper still, and is a question for the MFI interview. Real SMS in a month are capped by SMS_MONTHLY_LIMIT. With PILOT_SHOW_SMS=true, each SMS (real or simulated) is kept with its text, and the tester sees hers in "Mes SMS (pilote)" under Compte; the screen shows which were really sent. Testers can keep using made-up +228 numbers (no personal data collected); a real +250 number is only needed to receive a real SMS, with the tester's consent. A code that really reached her phone by SMS is no longer shown on screen in pilot mode (D61): it would let anyone holding the phone in without the SMS. A code that was only simulated, over the month's limit, or failed to send is still shown, so a tester is never stuck.

## Partners, money and data (20 Oct 2026)

### D33. The MFI sees group totals, not individual members; the ACEV is shared only at her request (20 Oct 2026)
The MFI that holds a group's money sees the group's total and the contribution amount set by its rules (for example 10 members x 5 000 FCFA = 50 000 FCFA due on Friday), not which member paid what. The per-member detail stays in Novi's ledger, visible to the group's own members. The MFI may use this data only to hold and pay out the money. A member's ACEV reaches an MFI only when she asks, to apply for credit, one request at a time; each share is recorded. The carnet is never shared by default. Reason: whoever holds the money necessarily sees the money, but traders may not want an institution to see each woman's payments; Ghana's e-levy showed informal workers pull back from tools they perceive as surveillance. To confirm in the MFI interview: whether anti-money-laundering rules require the MFI to identify each contributor, which may require a group account with named signatories rather than totals alone.

### D34. The MFI is invisible infrastructure; Novi orchestrates; the ACEV is portable (20 Oct 2026)
A licensed institution holds each group's money: an MFI partner, which members do not deal with directly. Members sign up, save and see everything in Novi; money screens show one line, "held at" the institution, for transparency. Novi never holds funds: under BCEAO Instruction 001-01-2024, Art. 2, payment services are reserved to banks, credit institutions, payment institutions, microfinance institutions and e-money issuers, and a tontine pot held for days or weeks also resembles savings, which banking and microfinance law reserve to licensed institutions. Considered: Novi collecting into its own FedaPay merchant balance (rejected: Novi would hold members' money without a licence) and members paying each other directly with Novi only recording (rejected: Novi could not run payouts automatically, its first differentiator). The ACEV belongs to the member and can be taken to any lender, not only the custodian (D33). Roadmap: if Novi scales, register under the lighter categories of the same instruction (account aggregation, Art. 3(40) and Art. 9; payment initiation, Art. 30 to 31), subject to legal advice; the instruction allows partnerships and forbids exclusivity (Art. 7), which supports working with several MFIs.

### D35. Identity is checked by scanning the e-ID card's QR code (20 Oct 2026)
Supersedes the typed-details step of D12. At sign-up the member scans the QR code on her e-ID card; Novi verifies ANID's signature on the data offline, which ANID describes as "verifiable offline and free of charge" (ID4Africa 2026), so there is no failed-ID queue for an MFI to handle. The scan proves the card is genuine, not that the person holding the phone owns it: one account per NIU and the SMS code to her phone remain, and the accredited online check through a licensed partner is the route to proving the holder. Until ANID publishes its QR format and signing key, the verifier uses a test key. A fallback is needed for members without a readable e-ID card (damaged card, card not yet issued).

### D36. Novi works with several MFIs, never exclusively (20 Oct 2026)
Each group's money is held by one licensed institution, chosen for the group; Novi can add further MFIs. BCEAO Instruction 001-01-2024, Art. 7, allows service partnerships and forbids exclusivity clauses. A member's ACEV can be taken to any of them.

### D37. Lenders see a member's detailed record only with her approval (20 Oct 2026)
The lender view shows one member's record: her payouts, her contributions, how regularly she paid, and any missed payments, because these inform the decision to grant a loan. It shows nothing until she approves access for a named lender. Each approval is for one lender, lasts a limited time, can be withdrawn, and every view is logged. Without her approval an MFI sees only group totals as custodian (D33). Considered: standing access for the custodian MFI (rejected: it turns the custodian into a monitor of each trader and conflicts with D33).
### D112. Group calls on Novi's own server, with no outside call service (7 Nov 2026)
Replaces Daily (D71, D85) as the default. Embedding Daily meant calling someone else's service; building the call layer shows how a group call actually works and makes Novi's own choices visible in code: who may enter (a signed pass), what the server sees (who is in which room, never the voice), and what the organiser controls. A side effect is that call details (names, addresses, who joined) no longer pass through a foreign company. The meetings and instant calls keep their rules (D71): a private room the size of the group, a personal pass per member valid until the room closes, the organiser as owner, microphone on, nothing recorded. What changes is who runs the room. The API now serves the call page itself (/call/<room>), opened inside Novi as before (D85), and a small signalling service (/v1/call-signal, a WebSocket) introduces the phones to each other. The voice then goes directly from phone to phone (WebRTC, audio only, each member connected to each other), so the server never carries or records it. The pass is signed by the server (HMAC with CALL_SECRET, or JWT_SECRET); a changed or expired pass is refused, a full room refuses newcomers, and the same member joining from a second phone replaces the first. The organiser can mute a member (a noisy market; the member can speak again herself) or take her out of the call, after which her pass no longer lets her back into that call. When the room's time is up, everyone is let go.
Limits, stated plainly. Each phone sends its voice to each other phone, which suits a group of up to about 6 to 8 speakers on a mobile connection (at about 30 kbit/s per voice, 7 others means about 200 kbit/s up); larger groups would need a relay server (an SFU), which is a production step. Phones find their public address through public STUN servers (Google's by default, CALL_STUN to change them); there is no TURN relay, so two phones behind strict operator NAT may not connect, and the page then suggests a voice note (D76). The microphone works only over HTTPS, so calls are tested against the Render server, not a local http address. A member with a basic phone cannot join; she follows on the organiser's speaker, and any decision is taken in Novi or by USSD. Daily stays coded and is used only with MEETINGS_PROVIDER=daily and DAILY_API_KEY.
